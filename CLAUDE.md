## Commands

```bash
npm install              # install deps
npx expo start            # start dev server (scan QR / press a,i,w)
npm run android            # start + open Android
npm run ios                # start + open iOS
npm run web                 # start + open web
npm run lint                 # expo lint (eslint.config.js, eslint-config-expo)
```

No test runner is configured in package.json. There is no `build` script — production builds go through EAS:

```bash
eas build --platform android --profile preview
eas build --platform ios --profile preview_ios
```

`EXPO_PUBLIC_API_BASE_URL` must point at a reachable backend for installed builds (see `.env.example`); EAS profiles in `eas.json` bake this in at build time. In `__DEV__` without that env var, `lib/api.ts` derives the API host from the Expo dev server's `hostUri` on port 5000; a release build without it falls back to `https://www.backend.thenura.care`.

App identity/config lives in `app.json` (source of truth) plus a thin `app.config.js` wrapper that only overrides `android.googleServicesFile` / `ios.googleServicesFile`. Those two files (`assets/google-services.json`, `assets/GoogleService-Info.plist`) are Firebase *client* configs and are git-tracked on purpose (their keys ship in every binary anyway; see `.gitignore`), so `app.json`'s paths work in EAS cloud builds. `app.config.js` still lets `process.env.GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICES_INFO_PLIST` (EAS **file**-type environment variables, set per-environment via `eas env:set --type file`, currently populated for `development`/`preview`/`production`) override them, falling back to the tracked files when those env vars aren't set. `eas.json`'s `preview_android`/`preview_ios` profiles don't match a canonical EAS environment name by profile name alone, so they carry an explicit `"environment": "preview"` to pull the same vars; `development`/`preview`/`production` profiles match by name automatically. Local Android signing (`credentialsSource: "local"` in most `eas.json` profiles) needs a gitignored `credentials.json` + `credentials/android/keystore.jks` in the project root — not committed, restore from the EAS keystore backup if missing (`eas credentials` can regenerate one only as a last resort, since Play Store update-signing requires the *same* key).

## Architecture

This is an Expo Router (v6, file-based routing) app — **frontend only**; the backend (`period-buddy-be`) lives in a separate repo/service and is consumed entirely through `lib/api.ts`.

### Provider stack (`app/_layout.tsx`)

```
ThemeProvider (components/theme.tsx)
  GenZModeProvider (components/genz-mode.tsx)  — purely cosmetic label-swap toggle (Profile → Preferences & Settings), AsyncStorage-persisted, no backend/auth dependency
    AuthProvider (components/auth-context.tsx)  — hydrates session from AsyncStorage before children render
      AppLockProvider (components/AppLock.tsx)  — PIN/biometric app lock, renders AppLockScreen overlay
        AppShell — waits for theme hydration, hides splash screen, renders <Stack/> + AppModalHost
```

`app/(app)/_layout.tsx` additionally wraps its subtree in `AppStateProvider` (`components/AppState.tsx`).

Modals are centralized: `components/modals/AppModalHost.tsx` is a single host rendered at the root, driven by `lib/modal-host.ts`. Prefer routing new modal UI through that host instead of ad hoc `Modal` components.

### Route groups (`app/`)

- `(tabs)/` — pre-auth flow: `login`, `signup`, `partner-connect`, and a `home` shown before onboarding.
- `(app)/` — authenticated app, one screen per top-level feature (tracker, habits, forest, consultation, community, blogs, reels, documents, document-chat, qa, qa-history, checkin-call, health-issues, hygiene, sexual-wellbeing, buddy-nomination, partner, app-lock, government-schemes, government-scheme-detail, scheme-applications, graphs-reports, symptom-report, ...), plus three "hub" screens — `care-hub`, `wellness-hub`, `explore-hub` — that each group several of those features behind one Home entry point (see below).
  - `(app)/(dashboard)/` — the main tab bar: `home`, `tracker`, `community`, `profile`.
    - `home.tsx` is intentionally short: greeting, stat pills, week strip, cycle-phase hero card, quick actions, an Insights carousel (See all → `predictions`), then a single "More for you" section with three `components/HubEntryCard.tsx` rows — `Care & Insights` → `(app)/care-hub.tsx` (predictions, daily insights, symptom trends/checker, graphs & reports, book-a-consult CTA), `Wellness & Support` → `(app)/wellness-hub.tsx` (health concerns, Nura AI, hygiene, sexual wellbeing, check-in call), `Explore` → `(app)/explore-hub.tsx` (forest, blogs, videos, partner sync, habits, buddy nomination). Add a new lightweight/browse destination to the matching hub screen's grid, not to Home directly — Home should stay a short dashboard, not grow back into a long list of tiles.
  - `(app)/(partner-view)/` — shown when the signed-in user is a connected partner "viewer" rather than the data owner (see `AuthUser.partnerRole`). Has its own floating tab bar (`_layout.tsx`) matching `(dashboard)/_layout.tsx`'s look exactly (same sizes/colors/center-avatar treatment): `overview` (read-only shared overview), `chat` (owner↔partner messaging), `voice` (center avatar, same mic-permission-gated voice assistant), `forum` (identical UI to the owner's — both re-export `components/screens/CommunityScreen.tsx`), `account` (partner's own account: notifications, app lock, disconnect, logout) — a code comment in `_layout.tsx` notes these names are deliberately distinct from the dashboard's tab names. `overview`'s notification bell pushes to the shared `(app)/notifications.tsx` screen — the same one the owner dashboard's bell opens — instead of its own bottom-sheet drawer, so the two roles see byte-identical notification UI; on focus it re-syncs `usePartnerViewState()`'s notifications so the bell's unread badge stays accurate after reading/marking things there. Cross-tab state (profile, notifications, live chat messages, the one WebSocket connection) lives in `components/partner-view-state.tsx`'s `PartnerViewStateProvider`/`usePartnerViewState()`, since Tabs screens are siblings and would otherwise each re-fetch/reconnect independently.

### Data layer (`lib/api.ts`)

All backend access goes through one file: typed request helpers (`apiRequest`, `apiEnvelopeRequest`) plus one `xApi` object per domain (`authApi`, `cycleApi`, `habitsApi`, `forestApi`, `consultationApi`, `subscriptionApi`, `partnerApi`, `buddyApi`, `nominationsApi`, `communityApi`, `blogsApi`, `reelsApi`, `healthIssuesApi`, `wellbeingApi`, `questionAnswerApi`, `voiceAgentApi`, `uploadApi`, `documentApi`, `speechApi`, `reportApi`, `insightsApi`, `screeningApi`, `schemesApi`, `schemeApplicationsApi`). Every response envelope is `{ data, error, message, ... }`; `apiRequest` unwraps `.data`, `apiEnvelopeRequest` returns the raw envelope (used for auth flows that need `token`/`user`/`isProfileComplete` alongside data). `healthApi` just wraps the `/health` liveness check.

- **Subscriptions / paywall** (`subscriptionApi`, `hooks/useSubscriptionAccess.ts`, `components/subscription/{LockedFeatureCard,PaywallModal,CouponField,FeatureGate}.tsx`, `app/(app)/subscription.tsx`): admins price individual features or bundles from the Content Studio (`period-buddy-be`'s `/api/admin/subscriptions/*`), and what's actually enforced server-side is driven entirely by that repo's `config/subscriptionRouteRegistry.js` — see its CLAUDE.md before assuming a given `hasAccess('key')` call here has a real backend gate behind it (nothing on the client can tell the difference between a wired key and an inert one; check the registry). `useSubscriptionAccess()` fetches `subscriptionApi.getMe()` once per mount (same shape as `useUserStats.ts`) and exposes `hasAccess('feature_key')`, plus `isLoading` — check `isLoading` before trusting a `false` from `hasAccess`, since it optimistically returns `true` until the first fetch resolves (so a locked screen never flashes its real content first). Three gating shapes are in use, pick per screen: (1) **action-level** — check `hasAccess(...)` right at the tap that starts the premium action (not deeper in the flow) and open `PaywallModal` when false, e.g. `CommunityScreen.tsx`'s new-post FAB, `symptom-checker.tsx`'s condition picker, `government-scheme-detail.tsx`'s Apply button, `qa-history.tsx`'s "+ New"/empty-state action, `partner.tsx`'s generate-invite-code button, `buddy-nomination.tsx`'s nominate action (checked *before* any optimistic state change, since that flow opens UI eagerly); (2) **whole-screen, hand-rolled** — `document-chat.tsx`, `checkin-call.tsx`, `documents.tsx`, `qa-history.tsx`, `government-scheme-detail.tsx` each inline the `locked`/`useEffect`/`LockedFeatureCard`/`PaywallModal` wiring directly (pre-dates the wrapper below); (3) **whole-screen, wrapped** — new screens should prefer `<FeatureGate featureKey="..." title="..." description="...">{content}</FeatureGate>` (`components/subscription/FeatureGate.tsx`) instead of reproducing shape (2)'s boilerplate — it renders `LockedFeatureCard`+`PaywallModal` in place of `children` while locked (so a locked screen's own data-fetching effects never even run) and the real content once unlocked; see `symptom-predictions.tsx` for the shape (split the screen into an inner `XContent()` component and wrap it). Whichever shape, also catch `isFeatureLockedError(err)` from the underlying API call as a fallback — the client-side check is only a cache, the server's registry-driven gate is the real one and can still 402 (a `402 FEATURE_LOCKED` response is parsed into `ApiError.kind === "featureLocked"` with a `.lock` payload carrying the feature's price and matching plans, so `PaywallModal` never needs a second fetch). Purchases run the same order→checkout→verify flow as `consultationApi` below, reusing `CashfreeCheckoutModal`/`CashfreeUpiCollectModal` as-is, with an optional coupon code (`CouponField`, shared between `PaywallModal` and `subscription.tsx`'s pricing grid — `subscriptionApi.applyCoupon()` previews a discount, `createOrder({..., couponCode})` redeems it; a 100%-off code returns `{free: true}` with no `orderId`/`keyId` at all, which both callers treat as "already unlocked, skip checkout entirely" via `finishFreeUnlock()`/the same inline handling in `subscription.tsx`). "My Subscription" (Profile → My Subscription) is the always-available pricing/purchase-history screen; `PaywallModal` is the reactive one shown when a lock is actually hit. `PaywallModal` itself is a `<Modal>`, and `CashfreeCheckoutModal`/`CashfreeUpiCollectModal` are also `<Modal>`s — two native Modals presenting at once is unreliable (the second one can silently fail to appear), so `PaywallModal` hides its own `visible` (`visible && !checkout`) the instant an order is created and only shows the checkout sheet; don't remove that guard when touching this file.

- `questionAnswerApi`'s `createSession`/`listSessions`/`getSession`/`sendSessionMessage`/`deleteSession` — `/api/questions/sessions*` (login-gated; `ask`/`getQuestions` above stay anonymous-friendly) — persisted Nura AI chat sessions, each optionally pinned to a topic (`lib/chatTopics.ts`'s `CHAT_TOPICS` — Periods & Cycle, Symptoms & Pain, Hygiene & Care, Mood & PMS, Sex & Intimacy, Nutrition & Wellness, and a catch-all Other/`general`; ids kept in sync with the backend's `utils/companionChat.js#CHAT_TOPICS`). Picking a topic chip scopes the session to just that topic, enforced two ways in `generateCompanionAnswer`: the system prompt (`topicScopeInstruction`) tells the model the restriction can't be lifted by anything the user says, and — since a model juggling "stay on topic" and "be helpful" in one breath will sometimes answer anyway by finding some loose thread back to the topic — a separate strict yes/no classification call (`isQueryOnTopic`) gates *both* the knowledge-base lookup and the AI call ahead of time; a NO short-circuits straight to a canned `offTopicReply()` without ever generating a real answer. "Other"/no topic skips this gate entirely and stays unscoped. The header's status line reflects the scope ("Focused on ‹topic›" vs "Private guidance online"). Each topic in `CHAT_TOPICS` also carries a short `intake` form (`ChatTopicIntakeQuestion[]`: `type: "choice"` single-select chips or `type: "input"` free text, either can be `optional`) shown after the chip is tapped instead of the old canned-question list; `composeIntakeMessage()` folds the answers into one opening chat message client-side; if a topic has no `intake` (currently just "Other") the old tap-a-suggested-question flow still applies. "Sex & Intimacy" additionally sets `minAge: 18`, checked both client-side (`isTopicLocked()` dims the tile with a lock icon) and again in `createChatSession` (`isTopicAgeRestricted()`, backed by the asker's profile `dateOfBirth`) — the client check is UX only, the server call is what actually blocks a session; a 403 from `createSession` is shown as a chat message instead of silently falling through to the unscoped stateless fallback below. The system prompt itself may now ask **one** short clarifying question before answering when a question is genuinely too ambiguous, instead of always answering blind. **`app/(app)/qa.tsx` is not the landing screen**: opened bare (no `?voiceMode=1`, `?sessionId=`, or `?new=1`) it immediately `<Redirect>`s to `app/(app)/qa-history.tsx`, which lists past chats first — every plain "Ask Nura AI" entry point (wellness-hub, tracker search, partner-view overview, ...) can therefore keep linking to bare `/(app)/qa` and still lands on the list; only the tab bar's center-avatar voice entry and qa-history's own "+ New"/row taps pass one of those three params to skip straight into a chat. A session is created lazily on the first message (never for idle browsing) and its id round-trips via `?sessionId=` so reopening a chat resumes it with full message history and the same topic scope; sending fails over to the stateless `ask()` + local knowledge base if the session call fails for a reason other than the age gate, same as before this feature existed, just without that turn being saved to history.
- `cycleApi.getSymptomPredictions()` — `GET /api/cycle/symptom-predictions`, per-symptom likelihood by cycle phase derived from the user's own logged history; powers `app/(app)/symptom-predictions.tsx`.
- `voiceAgentApi.checkinCall()` — `POST /api/voice-agent/checkin-call`, triggers an outbound "call me now" cycle check-in phone call (Samvaad voice agent) to the logged-in user's own phone number; powers `app/(app)/checkin-call.tsx` (Wellness & Support → Check-in Call). The screen persists an edited phone number via `authApi.updateProfile({ phone })` before triggering, since the backend always calls the number on the user's profile. Distinct from `voiceAgentApi.converse()` below, which is the in-app text/voice chat loop, not a real phone call. The same screen also has a recurring "auto check-in calls every cycle" toggle (`voiceAgentApi.get/saveCheckinCallSchedule()`, `GET`/`PUT /api/voice-agent/checkin-call/schedule`) — the actual firing happens server-side (`period-buddy-be`'s `utils/checkinCallScheduler.js`), ticked once a minute by that repo's `utils/inProcessScheduler.js` (in-process `setInterval`, the default — `ENABLE_IN_PROCESS_SCHEDULER=true`) or, for a multi-instance deployment, an external scheduler hitting `POST /api/voice-agent/checkin-call/scheduler-tick` with `ENABLE_IN_PROCESS_SCHEDULER=false` — **not** anything in this repo either way. If a saved schedule never actually calls, check that repo's README "Scheduled jobs" section first before assuming an app bug — the toggle can save successfully while `ENABLE_IN_PROCESS_SCHEDULER=false` with no external scheduler configured to replace it, in which case nothing is ever ticking (the manual "call me now" button still works in that state since it's a direct API call, not a scheduled one — don't take that as evidence the scheduler itself is fine).
- **Reminders & daily notifications**: the Cycle Settings sheet in `app/(app)/(dashboard)/tracker.tsx` already exposes `remindersEnabled`/`reminderDaysBefore`/`ovulationReminder`/`fertilityReminder` toggles (saved via `cycleApi`/`submitCycleSettings` onto `CycleSettings`), and `app/(app)/notifications.tsx` (bell icon, backed by `partnerApi.getNotifications()`/`markNotificationAsRead()` — the in-app notification list lives under `/api/partner` for historical reasons, not a dedicated notification API) already renders every `AppNotification["type"]` including `period_reminder`/`ovulation_reminder`/`habit_reminder`. What actually *creates* those reminder notifications is `period-buddy-be`'s `utils/dailyNotificationScheduler.js` — same external-scheduler pattern as the check-in call tick above, `POST /api/notifications/daily-tick` once a day — which reads those same CycleSettings toggles and also sends a once-daily "log today" nudge (`type: "system"`) when the user hasn't logged anything yet that day. Every `Notification` doc triggers its own push send automatically via its Mongoose post-save hook (FCM, `period-buddy-be`'s `utils/fcm.js`, skipped when the user's `notificationsEnabled` profile toggle is off) to whatever native FCM/APNs token (`getDevicePushTokenAsync`, not an Expo push token — the backend uses firebase-admin directly) `authApi.updateFcmToken()` last registered. `lib/notifications.ts` owns all of it: `setNotificationHandler` (foreground banners), the Android channel `ANDROID_CHANNEL_ID = 'default'` (must match `utils/fcm.js`'s `android.notification.channelId`; created before the permission prompt, which Android 13+ requires), `requestNotificationPermissionAsync()` (permission only — used by the pre-login `components/PermissionsGate.tsx`), `registerForPushNotificationsAsync()` (permission + token upload — only with a session; `auth-context.tsx` calls it on every launch/login and also subscribes `addPushTokenRefreshListener()` for FCM token rotation), and `enablePushOnDeviceAsync()` (Profile/partner Account notifications toggle switched on → re-asks or offers Settings). Logout (`POST /api/logout`) clears the token server-side, and uploading a token strips it from any other account that had it. Tap routing is `resolveNotificationTarget(data, isViewer)` in `lib/notifications.ts`, used both by `app/_layout.tsx` (push taps — queued until the navigator/auth are ready and the entry screens have redirected, then resolved with the signed-in role) and by rows in `app/(app)/notifications.tsx`: an explicit `data.route` (or `data.url`, validated to be an in-app path — admin broadcasts from the Content Studio's "Opens in the app" picker set this) wins, then `NOTIFICATION_TAP_ROUTES`/`PARTNER_VIEWER_TAP_ROUTES` by `type` (partner viewers get partner-view equivalents; the `system` daily nudge with `data.kind === "daily_nudge"` goes to the tracker), else the notifications list.
- `insightsApi.getDaily()` — `GET /api/insights/daily`, personalized daily hormone/mood/energy/skin insight plus exercise/nutrition/sleep/wellness suggestion lists; powers `app/(app)/insights.tsx`.
- `screeningApi` (`getQuestions`, `submitAssessment`, `getHistory`) — `/api/screening/*`, the PCOS/endometriosis/fibroid/thyroid symptom checker flow; powers `app/(app)/symptom-checker.tsx`.
- `schemesApi` / `schemeApplicationsApi` — `/api/schemes/*` and `/api/scheme-applications/*`, the Government Schemes & Benefits feature (women's reproductive & menstrual health schemes; Central + Rajasthan, state-independent architecture). Powers `app/(app)/government-schemes.tsx` (listing/search/category & Central-Rajasthan filters/recommended), `government-scheme-detail.tsx` (detail + eligibility checker + action buttons keyed by `actionType`: `APPLY`/`CHECK_ELIGIBILITY`/`FIND_FACILITY`/`LEARN_MORE`/`EXTERNAL_APPLICATION` — not every scheme is an "apply"), and `scheme-applications.tsx` (My Applications). Reached from Profile → Government Schemes & Benefits. Pure display/logic helpers live in `lib/schemeHelpers.ts` (unit-tested in `lib/__tests__/`). Eligibility never claims a guarantee — only "You may be eligible". A `FIND_FACILITY` scheme's primary CTA opens a Google Maps government-hospital search (`schemeHelpers.governmentHospitalMapsUrl(user.state)`) — **not** the scheme's `officialUrl`, which is an info page and stays on the secondary "Official Website" button. Admins create/edit/delete schemes from the separate `period-buddy-content` web portal (Content Studio), not the mobile app; the app is read-only over `/api/schemes/*`.
- `app/(app)/graphs-reports.tsx` (Profile → Graphs & Reports) is a colorful gradient-card dashboard — Cycle length (last 3 lengths from `cycleApi.getPredictions().analyticsData` as proportional pill bars), Weight and Basal body temperature (latest logged value, derived client-side from `cycleApi.getMonthLogs()` over the last 3 months — there's no backend aggregate for these two yet), and Water intake / Sleep (90-day averages from `reportApi.getHealthReport(...).cycle.averages`) — plus a Reports section linking to `symptom-report.tsx` and to Documents' existing "Download doctor report" flow (`router.push({ pathname: "/documents", params: { openReport: "1" } })`, which `documents.tsx` reads via `useLocalSearchParams` to auto-open its report modal pre-filled to the last 90 days). `app/(app)/symptom-report.tsx` renders `reportApi.getHealthReport(...).cycle`'s `symptomCounts`/`moodCounts`/`flowCounts` as ranked bar lists plus the sleep/water/stress averages — a read-only "review your symptoms and cycle" view, distinct from the downloadable PDF.

- `lib/cycle.ts` is the canonical source for the `CyclePhase` type and `getCyclePhase(cycleDay, periodLength, cycleLength)` — import it instead of re-deriving cycle phase locally (tracker, forest, symptom predictions, and `DayEntry.phase` in `lib/api.ts` all use it).
- **Cross-screen refresh (`lib/data-sync.ts`, `hooks/useDataRefresh.ts`)**: dashboard tabs and any screen lower in the stack stay mounted, so a one-time fetch-on-mount goes stale when another screen writes. `apiEnvelopeRequest` calls `emitMutation()` after every successful non-GET, and `topicsForMutation()` maps the endpoint to `DataTopic`s (`cycle`, `dashboard`, `profile`, `subscription`, `notifications`, `qaSessions`, `schemeApplications`, `documents`, `partner`, ...; unit-tested in `lib/__tests__/data-sync.test.ts`) — so writes need no manual wiring, but a **new endpoint that changes data another screen shows must be added to `MUTATION_TOPICS`** (requests that bypass the helper, like `documentApi.upload`, call `emitDataChange` by hand; so does a foreground push, via `app/_layout.tsx`). Screens subscribe with `useDataRefresh(topics, cb)` — `cb` runs (debounced) immediately if the screen is focused, otherwise once on its next focus, with `{ whileFocused }` so a screen can skip refetching over its own writes (profile, partner) or do a lighter refetch (tracker) — or with `useAsyncLoad(fetcher, deps, { refreshOn })`. Callbacks must refetch silently (no loader, keep data on failure). `useUserStats`/`useSubscriptionAccess` also drop their 60s module cache on `dashboard`/`subscription`, which is what makes `FeatureGate` unlock after a purchase.
- `hooks/useUserStats.ts` is the canonical source for streak/wallet numbers (`{ streakCount, walletBalance }`); it fetches the dashboard once and syncs it into auth-context. Screens should consume this hook instead of reading `user.streakCount`/`user.walletBalance`/`user.tokenEarned` directly, so streak/points never drift between screens.
- Auth token is stored in AsyncStorage under `period-buddy.auth-session` (`AUTH_SESSION_KEY`) and attached as `Authorization: Bearer` automatically; pass `skipAuth: true` for public endpoints.
- `AuthUser.partnerRole` is resolved client-side after login (`lib/auth.ts#connectPartnerAndResolveRoute`) and never comes back on server user objects, so `auth-context.tsx#updateUser` keeps the existing role unless the caller passes one explicitly (`null` included, as on partner disconnect) — otherwise passing a fresh `authApi.updateProfile()` result would drop it and the partner-view layout guard would bounce a viewer into the owner dashboard. Because the role otherwise lives only on-device, `AuthProvider` re-syncs it from `partnerApi.getProfile()` (`syncPartnerRole`) on every launch/login and app foreground, and `PartnerViewStateProvider.refreshProfile()` pushes the fresh profile's role in too — so an owner-side disconnect (server sets the viewer's role to `null`) or a failed role lookup at login self-corrects via the layout guards. A sequence counter (`roleWriteSeq`) drops sync results that started before a sign-in/out or explicit role write, so the post-login sync can't race `connectPartner()` and overwrite the fresh `viewer` role. `DELETE /api/partner/disconnect` also emits a `partner_disconnected` WebSocket event to both sides' personal `user_<id>` rooms (plus a push to the other side): the partner view re-fetches on it (→ role sync → guard redirect) and the owner's `(app)/partner.tsx` reloads its profile, so either side ending the connection updates the other immediately.
- A 401 triggers a global `onUnauthorized` handler registered by `AuthProvider`, which clears the local session — don't hand-roll 401 handling per screen. A response with `code: "ACCOUNT_SUSPENDED"` (403 from login/Google sign-in, 401 mid-session — see `period-buddy-be`'s `utils/accountStatus.js`) becomes `ApiError.kind === "accountSuspended"` (`isAccountSuspendedError()`); on an authenticated request it calls `onUnauthorized("suspended")`, and `AuthProvider` signs out and shows one "Account suspended" alert. On the login screens the server's message just shows in the existing error banner.
- Every request is aborted after `DEFAULT_TIMEOUT_MS` (20s; override per-call with `timeoutMs`, `0` disables) and every failure throws a typed `ApiError` carrying `kind` (`network`/`timeout`/`server`/`notFound`/`unauthorized`/`unknown`) and `status`. Use the exported `isNetworkError(err)` and `getFriendlyErrorMessage(err)` helpers to branch on connectivity vs. show copy — don't string-match `.message`. `useAsyncLoad` already exposes an `offline` boolean derived from these; `LoadingErrorState` and `EmptyState` take an `offline`/`wifi-off` variant.
- Several types carry `@deprecated` fields kept for backend backward-compat (e.g. `tokenEarned` → `walletBalance`, `likes` → `likeCount`, `views`/`viewsCount` → `viewCount`) — use the non-deprecated field in new code.
- File uploads (`uploadApi.uploadImage`, `documentApi.upload`, `speechApi.transcribe`) bypass the JSON helpers and build `FormData` directly, with a web-vs-native branch (web needs a real `Blob`, native uses the RN `{uri,name,type}` shape).
- Realtime (buddy chat, video call signaling) goes over a WebSocket at `WS_BASE_URL` — construct the URL via `getWebSocketUrl()` so the auth token query param is attached consistently.

### Sharing & deep links

`lib/share.ts` (`shareWithAppLink`, used via `components/AppState.tsx`'s `sharePost` or directly) is the one way to share anything that should reopen in-app: it wraps an in-app path (e.g. `"community?postId=abc123"`) into `https://thenura.care/app?deeplink=<path>`. Don't call `Share.share` directly for shareable in-app content. Current share points and their deeplinks: blog detail (`blogs?slug=`), reel cards in blogs and the Share button on each reel in `reels.tsx` (`reels?reelId=`), community posts (`community?postId=`), government scheme detail header (`government-scheme-detail?id=<slug>`), partner invite (`partner-connect?code=`), symptom checker results (`symptom-checker`). **Every deeplink route's first path segment must be in `lib/deeplink.ts#SHAREABLE_ROUTES`**, or incoming links to it are ignored (the app just opens). Target screens read their id with `useLocalSearchParams` and open the item themselves after mount (blogs → article modal, community → comments sheet, reels → fetches that reel via `getReelById` and pins it first/playing, scheme detail → loads by `id`, partner-connect → prefilled code).

Incoming links: `app/+native-intent.tsx#redirectSystemPath` (expo-router's pre-routing hook, cold start and warm) runs every URL through `lib/deeplink.ts#resolveDeepLink`, which recognizes both `https://thenura.care/app?deeplink=<path>` (Android App Link) and `thenura://<route>?...` for shareable routes; anything else (OAuth redirects, dev-client URLs) passes through untouched. For ours it *queues* the target in `lib/deeplink.ts` and returns `/` (cold) or `""` (warm, = don't navigate), so expo-router never lands on the unmatched `/app` route. `AppShell` in `app/_layout.tsx` consumes the queue (`useSyncExternalStore`) and `router.push`es it once the navigator is ready, the user is signed in, and the entry screens (`ENTRY_PATHS`) have redirected to the dashboard — so Back returns to the dashboard, and a logged-out user's link stays queued (in memory) until they log in. `PUBLIC_DEEP_LINK_PATHS` (just `/partner-connect`) opens without waiting for login. `/community` is rewritten to `/forum` for partner viewers. Every push adds an `openedAt` timestamp param so an already-mounted screen (the community tab) re-opens the item when the same link is tapped twice. Don't add a separate `Linking` listener for these — that was the old duplicate handling.

Android App Links: `app.json`'s `android.intentFilters` (https, `thenura.care`, `pathPrefix: /app`, `autoVerify: true`) needs `https://thenura.care/.well-known/assetlinks.json` (marketing site repo `The-Nura-Marketing-Website/public/.well-known/`, served as JSON by its `vercel.json`) to list the **Play Console App signing key SHA-256** — until that fingerprint is filled in and deployed, Android won't verify and the https link opens the browser instead. The browser fallback is that repo's `src/pages/AppRedirect.jsx` (`/app` route): on Android it navigates to `intent://<deeplink>#Intent;scheme=thenura;package=com.uvin124.thenura;S.browser_fallback_url=<Play Store with referrer=deeplink=...>;end` (works in Chrome and most in-app browsers; also offered as a button since some webviews need a real tap), iOS/desktop get buttons. The Play Store `referrer` is set but not read by the app yet (no install-referrer library, so no deferred deep link after a fresh install). `ios.associatedDomains` + `apple-app-site-association` (placeholder Team ID) are there for when iOS ships. Intent filter / scheme changes need a new native build; test with `adb shell am start -a android.intent.action.VIEW -d "<url>"`.

### Styling

NativeWind (Tailwind for RN) via `tailwind.config.js` / `global.css`, plus `components/theme.tsx` (light/dark, hydrated before first paint) and `components/ui-tokens.ts` for shared design tokens (including `getSeverityColor` for danger/warning/success by numeric threshold). `ThemeColors` has two extra category accents beyond the rose/lavender/mint trio — `sky` (blue) and `gold` — added for the day-log modal and Graphs & Reports; `getSoftTints`/`getLogCategoryTints` (`ui-tokens.ts`) expose them alongside the rest as pale-bg/solid-fg pairs.

**Fonts:** exactly two typefaces app-wide — Manrope (`fonts.heading`/`fonts.body`) for all headings and body copy, IBM Plex Mono (`fonts.mono`/`fonts.monoSemiBold`) for numeric/code-like content (streaks, OTPs, stats). Both are loaded once in `app/_layout.tsx` via `useFonts` (alongside the `Ionicons`/`Feather`/`MaterialCommunityIcons` icon fonts, preloaded behind the splash so icons don't pop in late — add any new `@expo/vector-icons` family there too); don't add other font families without updating `ThemeFonts` there too. Since NativeWind's `font-*` classes only set `fontWeight` (no `fontFamily` in `tailwind.config.js`), `app/_layout.tsx` also sets `Text`/`TextInput` `defaultProps.style` to Manrope so anything that omits an explicit `fontFamily: fonts.body` still renders consistently instead of falling back to the OS default — explicit `fontFamily` on a component still overrides this default.

### Shared screen scaffolding

`components/ScreenHeader.tsx` (back button + title) and `components/LoadingErrorState.tsx` (full-screen loading/error-with-retry) cover the common shape of simple detail screens; its default loading state is the branded `components/Loader.tsx` (bear mascot inside a pulsing/rotating themed ring — use it, or `<Loader fullscreen />`, instead of a bare `ActivityIndicator` for page-level waits); `hooks/useAsyncLoad.ts` collapses the load-on-mount + pull-to-refresh + error-state boilerplate around a single fetcher. **Paged lists**: `hooks/usePaginatedList.ts` (`fetchPage(page) → { items, hasMore }`; returns `items`/`setItems`/`loading`/`refreshing`/`error`/`offline`/`hasMore`/`loadingMore`/`loadMore`/`reload`, dedupes by `_id`/`getKey`, and its `refreshOn` background refresh merges page 1 over the top instead of collapsing opened pages) plus `components/LoadMoreButton.tsx` ("Show more") — used by notifications, qa-history; documents and the older blogs/government-schemes/scheme-applications screens hand-roll the same page/hasMore/loadingMore shape. Mutate rows in place with `setItems` (e.g. mark read, delete) rather than `reload()`, which would collapse the list back to page 1. `hasMorePages(pagination)` (`lib/api.ts`) is the one "is there another page" check. Endpoints that used to return bare arrays expose paging on the *envelope* (`partnerApi.getNotificationsPage`, `questionAnswerApi.listSessionsPage` go through `apiEnvelopeRequest`, since `apiRequest` drops everything but `data`); see `period-buddy-be`'s CLAUDE.md "Pagination". Home's bell dot uses `getNotificationsPage({ limit: 1 }).unreadCount` instead of downloading the list. `components/EmptyState.tsx` is the shared placeholder for lists/sections that loaded fine but came back empty (distinct from an error; supports a `compact` in-list variant and an optional action button) — use it instead of ad hoc empty copy. `lib/format.ts` holds small shared date formatters — `formatShortDate`, plus `getDateKey`/`getMonthKey` (local-timezone `YYYY-MM-DD`/`YYYY-MM` keys, used by the tracker calendar and the Graphs & Reports / Symptom report screens to index a day's log) — instead of re-deriving these per-screen. Prefer these over re-implementing the same screen shell.

A full screen shared verbatim across route groups (not just scaffolding) lives in `components/screens/` — e.g. `CommunityScreen.tsx`, re-exported by both `(dashboard)/community.tsx` and `(partner-view)/forum.tsx` — so the two roles can never visually drift apart on a screen that should look identical for both.

### Tracker calendar (`app/(app)/(dashboard)/tracker.tsx`)

The calendar card still renders all 12 months of the selected year stacked and scrollable (`calendarMonths`), but the initial landing on the current month is instant, not animated: the month list stays hidden (`calendarRevealAnim`, opacity 0), and its container clamped to `CALENDAR_LOADING_HEIGHT` with `overflow: hidden` (a `Loader` sits over that clamped area), until the first `scrollTo({ animated: false })` — driven by `monthLayouts` from each month's `onLayout` — has landed on `selectedMonthIndex` (initialized to today), then fades in already positioned there, so opening the tracker never shows a visible "scrolling to current month" motion. `hasInitialScrolled` (a ref, claimed the instant the jump is scheduled — not after it runs, so a second `onLayout` arriving in between can't schedule a duplicate one) gates that one-time instant jump. Expanding the container to its true height (`setIsCalendarRevealed(true)`) and calling `scrollTo` are deliberately **not** in the same tick: the container's expansion is itself a state update the native/DOM side hasn't re-measured yet, so a same-tick `scrollTo` targets a y position beyond what the still-clamped content currently allows and silently comes up short (reproduces identically on native and web — this bit it before, see git blame if it regresses again). A nested double `requestAnimationFrame` after `setIsCalendarRevealed(true)` waits for that re-layout to actually land (one frame for React's re-render, one for the paint) before scrolling and starting the fade. Every later month change (chevrons, the "Today" pill shown once you've navigated away from the current month) scrolls smoothly instead, since by then the container is already at full height and it's a deliberate, visible action. The 4-phase legend (`phaseLegendRow`) is defined once and rendered twice — inline at the top of the calendar card, and as a floating copy in the fixed header (`showFloatingLegend`, compares live page scroll offset `pageScrollY` against the calendar card's measured top `calendarSectionY`) that takes over once the in-card legend has scrolled out of view, so the phase colors stay reachable without scrolling back to the top.

### Day-log modal (`components/DayDetailsModal.tsx`)

Opened from the tracker calendar (and Home's Log period/Symptoms/Mood quick actions, via `focusSection`). Every option chip renders as an icon-in-a-colored-circle pill via `renderOption`'s `tint` param, one `getLogCategoryTints()` color per section (Menstrual flow=rose, Ovulation symptoms=success, Sex and sex drive=danger, Mood=accent, Physical symptoms=warning, Vaginal discharge=sky, Digestion and stool=secondary, Pregnancy test=gold, Physical activity=success) — selected state fills the icon circle solid and washes the pill background with the same tint. Categories that already have a typed, backend-owned `DayEntry` field (`flow`, `discharge`, `digestion`, `mood`/`moods`, `skin`, `exercise`) keep using it; categories the backend has no field for (Ovulation symptoms, Sex and sex drive, Pregnancy test, "Blood clots", four extra discharge descriptors, "Nausea") are logged as plain tags into the existing free-form `DayEntry.symptoms: string[]`, so none of that needed a backend change. `MOOD_OPTIONS` (`ui-tokens.ts`) covers the full mood grid, including several `MoodValue`s newer than what `period-buddy-be` (a separate repo, not in this workspace) may validate — if that service enforces `mood`/`moods` as a strict enum, it needs the new values (`frisky`, `moodSwings`, `depressed`, `guilty`, `obsessive`, `lowEnergy`, `apathetic`, `confused`, `selfCritical`) added server-side too.

### Wellness Forest (`app/(app)/forest.tsx`)

`components/ForestScene.tsx` is the ambient sky/hills/weather backdrop (ported from the marketing site, mood set by `CyclePhase`). `components/GrowthTree.tsx` is the actual personal-progress visual: a single tree whose growth stage (`seed → sprout → sapling → tree → bloom`, via `getGrowthStage(health)`) and color vitality are driven entirely by `ForestStatus.currentHealth` (0–100) from `forestApi.getStatus()` — grows a stage with a bounce when care is logged (`isWatering`), droops/dulls when `!todayCareLogged` (`isThirsty`), and reverses smoothly in either direction since it's one continuous scale, not separate "grew"/"wilted" states. `forest.tsx` passes it into `ForestScene`'s `centerpiece` prop, which swaps out the scene's generic 4-species decoration for "your tree in your forest," and reuses the same component (smaller, no thirst) to render each past cycle in the Cycle Tree Logs history list, so live and historical tree states share one visual language.

### Voice input

`hooks/useVoiceInput.ts` wraps `expo-audio` recording (with metering enabled) behind `{ handleMicPress, isRecording, isTranscribing, level }`: tap-to-start/tap-to-stop always works, and when `voiceMode` is true it also auto-stops and transcribes after ~3s of on-device silence (via live dB metering), calling `onTranscript`. `components/VoiceOrb.tsx` is the reusable animated mic (Reanimated pulsing rings driven by `level`, themed via `colors.primary`/`colors.accent`/`colors.danger`). `components/VoiceModeOverlay.tsx` is a full-screen `Modal` — centered large `VoiceOrb`, rotating sci-fi sweep rings, and a status line (listening/thinking/speaking) — that `app/(app)/qa.tsx` and `app/(app)/document-chat.tsx` render whenever `voiceMode` is true; both screens also run a small effect that auto re-arms the mic (`handleMicPress`) whenever voice mode is idle (not recording/transcribing/replying/speaking), so the mic opens automatically on entering voice mode and after each spoken reply, Assistant-style.

### Platform-specific files

Some components have a `.web.tsx` variant (e.g. `components/BuddyVideoCall.tsx` / `.web.tsx`) for APIs that differ between native and web (WebRTC), and `components/CashfreeCheckoutModal.tsx` / `.web.tsx` (`react-native-webview` ships no web implementation at all — its fallback just renders "React Native WebView does not support this platform" — so the web variant loads Cashfree's JS SDK directly via a `<script>` tag and opens its real browser checkout instead of a WebView; same `onResult` shape either way, so callers never branch on platform). `components/CashfreeUpiCollectModal.tsx` (no web variant needed — it's a plain in-app UPI-ID form) is the other half of the checkout flow; see the "Subscriptions / paywall" bullet above and `consultationApi` below for how the two combine. `reels.tsx` and `documents.tsx`'s in-app document/PDF viewer also use `react-native-webview` directly (not through a shared component) and currently hit the same "not supported" fallback on web — no `.web.tsx` fix exists for those yet.
