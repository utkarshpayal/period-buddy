## Commands

```bash
npm install              # install deps
npx expo start            # start dev server (scan QR / press a,i,w)
npm run android            # start + open Android
npm run ios                # start + open iOS
npm run web                 # start + open web
npm run lint                 # expo lint (eslint.config.js, eslint-config-expo)
```

No test runner is configured in package.json. There is no `build` script — production builds go through EAS:

```bash
eas build --platform android --profile preview
eas build --platform ios --profile preview_ios
```

`EXPO_PUBLIC_API_BASE_URL` must point at a reachable backend for installed builds (see `.env.example`); EAS profiles in `eas.json` bake this in at build time. In `__DEV__` without that env var, `lib/api.ts` derives the API host from the Expo dev server's `hostUri` on port 5000; a release build without it falls back to `https://www.backend.thenura.care`.

App identity/config lives in `app.json` (source of truth; Android builds both `armeabi-v7a` and `arm64-v8a` so 32-bit budget phones can install it; the adaptive launcher icon is `assets/images/brand/adaptive-foreground.png` (logo scaled into the 66% safe zone, on white) plus `adaptive-monochrome.png` for Android 13+ themed icons — regenerate both from `app-icon.png` if the logo changes) plus a thin `app.config.js` wrapper that only overrides `android.googleServicesFile` / `ios.googleServicesFile`. Those two files (`assets/google-services.json`, `assets/GoogleService-Info.plist`) are Firebase *client* configs and are git-tracked on purpose (their keys ship in every binary anyway; see `.gitignore`), so `app.json`'s paths work in EAS cloud builds. `app.config.js` still lets `process.env.GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICES_INFO_PLIST` (EAS **file**-type environment variables, set per-environment via `eas env:set --type file`, currently populated for `development`/`preview`/`production`) override them, falling back to the tracked files when those env vars aren't set. `eas.json`'s `preview_android`/`preview_ios` profiles don't match a canonical EAS environment name by profile name alone, so they carry an explicit `"environment": "preview"` to pull the same vars; `development`/`preview`/`production` profiles match by name automatically. Local Android signing (`credentialsSource: "local"` in most `eas.json` profiles) needs a gitignored `credentials.json` + `credentials/android/keystore.jks` in the project root — not committed, restore from the EAS keystore backup if missing (`eas credentials` can regenerate one only as a last resort, since Play Store update-signing requires the *same* key).

## Architecture

This is an Expo Router (v6, file-based routing) app — **frontend only**; the backend (`period-buddy-be`) lives in a separate repo/service and is consumed entirely through `lib/api.ts`.

### Provider stack (`app/_layout.tsx`)

```
ThemeProvider (components/theme.tsx)
  GenZModeProvider (components/genz-mode.tsx)  — purely cosmetic label-swap toggle (Profile → Preferences & Settings), AsyncStorage-persisted, no backend/auth dependency
    AuthProvider (components/auth-context.tsx)  — hydrates session from AsyncStorage before children render
      AppLockProvider (components/AppLock.tsx)  — PIN/biometric app lock, renders AppLockScreen overlay
        AppShell — waits for theme hydration, hides splash screen, renders <Stack/> + AppModalHost
```

`app/(app)/_layout.tsx` additionally wraps its subtree in `AppStateProvider` (`components/AppState.tsx`).

Modals are centralized: `components/modals/AppModalHost.tsx` is a single host rendered at the root, driven by `lib/modal-host.ts`. Prefer routing new modal UI through that host instead of ad hoc `Modal` components.

### Route groups (`app/`)

- `app/index.tsx` — logged-out welcome: 3 swipeable value slides, then "Get started" (→ signup), "I already have an account" (→ login) and the partner-invite link. There is no first-launch permissions screen: notifications are asked on onboarding's finish screen, microphone and photos the first time a feature needs them.
- `(tabs)/` — pre-auth flow: `login`, `signup` (Google first, then first name + email + password with a live rule checklist from `lib/password.ts`, which mirrors the backend's `validatePasswordStrength`; last name is optional and not asked; consent is the "By continuing…" line linking thenura.care/terms and /privacy), `partner-connect`.
- **First-run setup** (`components/onboarding/OnboardingFlow.tsx`, pure logic in `lib/onboarding.ts`, unit-tested): shown by `(dashboard)/_layout.tsx` while `user.isProfileComplete === false`. One question per screen: goals → last period start (month grid, or "I don't remember" → rough ranges) → period length → cycle length (steppers, "Not sure" uses 5/28) → birthday (`components/BirthdayInput.tsx`, typed DD/MM/YYYY boxes, 13+) → a finish screen with the first prediction and the notification soft-ask. Answers are saved per user in AsyncStorage so a killed app resumes where it left off. The last question saves the profile and cycle settings together; a failure shows inline with retry. `auth-context` holds off push registration until setup is done (except for partner viewers, who never see it). Phone and photo are not asked here: they're optional and live in `(app)/edit-profile.tsx` (Profile → Edit profile, plus a "Complete your profile" card while either is missing).
- `(app)/` — authenticated app, one screen per top-level feature (tracker, habits, forest, consultation, community, blogs, reels, documents, document-chat, qa, qa-history, checkin-call, health-issues, hygiene, sexual-wellbeing, buddy-nomination, partner, app-lock, government-schemes, government-scheme-detail, scheme-applications, graphs-reports, symptom-report, ...), plus three "hub" screens — `care-hub`, `wellness-hub`, `explore-hub` — that each group several of those features behind one Home entry point (see below).
  - `(app)/(dashboard)/` — the main tab bar: `home`, `tracker`, `community`, `profile`.
    - `home.tsx` is intentionally short: greeting, stat pills, week strip, cycle-phase hero card, quick actions, an Insights carousel (See all → `predictions`), then a single "More for you" section with three `components/HubEntryCard.tsx` rows — `Care & Insights` → `(app)/care-hub.tsx` (predictions, daily insights, symptom trends/checker, graphs & reports, book-a-consult CTA), `Wellness & Support` → `(app)/wellness-hub.tsx` (health concerns, Nura AI, hygiene, sexual wellbeing, check-in call), `Explore` → `(app)/explore-hub.tsx` (forest, blogs, videos, partner sync, habits, buddy nomination). Add a new lightweight/browse destination to the matching hub screen's grid, not to Home directly — Home should stay a short dashboard, not grow back into a long list of tiles.
  - `(app)/(partner-view)/` — shown when the signed-in user is a connected partner "viewer" rather than the data owner (see `AuthUser.partnerRole`). Has its own floating tab bar (`_layout.tsx`) matching `(dashboard)/_layout.tsx`'s look exactly (same sizes/colors/center-avatar treatment): `overview` (read-only shared overview), `chat` (owner↔partner messaging), `voice` (center avatar, same mic-permission-gated voice assistant), `forum` (identical UI to the owner's — both re-export `components/screens/CommunityScreen.tsx`), `account` (partner's own account: notifications, app lock, disconnect, logout) — a code comment in `_layout.tsx` notes these names are deliberately distinct from the dashboard's tab names. `overview`'s notification bell pushes to the shared `(app)/notifications.tsx` screen — the same one the owner dashboard's bell opens — instead of its own bottom-sheet drawer, so the two roles see byte-identical notification UI; on focus it re-syncs `usePartnerViewState()`'s notifications so the bell's unread badge stays accurate after reading/marking things there. Cross-tab state (profile, notifications, live chat messages, the one WebSocket connection) lives in `components/partner-view-state.tsx`'s `PartnerViewStateProvider`/`usePartnerViewState()`, since Tabs screens are siblings and would otherwise each re-fetch/reconnect independently.

### App CMS (remote layout)

The separate **The-Nura-CMS** portal controls parts of the app through `period-buddy-be`'s public `GET /api/app-config`, so none of this needs a release.

**Files:**
- `lib/appConfig.ts`: pure types, parsing, selectors and tests (`lib/__tests__/appConfig.test.ts`).
- `components/app-config.tsx`: `AppConfigProvider`, which sits above `ThemeProvider`.
- `hooks/useViewer.ts`: who is looking, for audience rules.
- `lib/tapAction.ts`: runs tap actions (in-app routes go through the launch route guard).
- `lib/launchGuard.ts`, `components/AppConfigSync.tsx`, `components/LaunchSheet.tsx`, `components/LaunchTileParts.tsx`, `lib/deviceId.ts`: launch states (below).

**What the CMS controls:**
- **Feature tiles:** which of the built-in `FEATURE_REGISTRY` features show, and where. The places are the three hubs plus a **Shortcuts** block on Home (`home` placement, the `shortcuts` home section, last in the default order) and Profile (`profile`, via `components/CmsShortcuts.tsx`, which draws them as rows of four round quick-action icons with labels and no heading, ignoring tile size).
- **Tile look:** order, size (`small` grid tile or `large` row), colour, text, badge and audience (signed-in / premium / free, platform, app-version range).
- **Admin link tiles** (`customTiles`): open a route, a website (`expo-web-browser`), or **another app** via `Linking.openURL(value)`, falling back to `fallbackUrl`. A tile with no action (`type: "none"`, or an unsafe one parsed down to it) is a Coming soon teaser for something not in the app yet: it shows only while locked, and `hubTilesFor` drops it for anyone it would resolve to `open` for.
- **Screen layouts:** order and visibility of the blocks on Home (`homeSections`), Profile and the three hubs (`screenSections`, read with `shownSections(config, screen, viewer)`, which also applies each block's `audience` and `startAt`/`endAt`). `sectionText` gives a block's heading/intro override, and `screenTitles` renames hubs (also on Home's hub cards). The hubs share `components/HubScreen.tsx` (intro line, promo banners, tiles). Blocks in `REQUIRED_SECTIONS` (Profile's identity, account, preferences, privacy & help, log out; a hub's tiles) always show, for everyone, whatever the config says.
- **Feature usage** (`lib/usage.ts`): `AppConfigSync` counts an `open` when a feature's screen is entered (`featureForRoute`), `useTilePress` a `tap` on an open tile; batched to `POST /api/app-config/usage` every 15 s, at 20 events or on backgrounding. Fire and forget.
- **Theme:** brand, surface and text colour overrides per mode, merged into `components/theme.tsx`.
- **Promo banners** (`components/PromoBanners.tsx`): Home top/middle slots, hubs and Profile, plus a once-per-device **popup** over Home (`components/PromoPopup.tsx`, its own `Modal` because `AppModalHost` only renders alerts). Clicks and impressions are beaconed, impressions once per session.
- **Launch states** (spec: The-Nura-CMS `docs/launch-states.md` §4 and §7.3): each feature and link tile carries a `launch` the backend has already decided for this user or device. The values are `open`, `soon` (Coming soon: a dimmed tile with a SOON pill replacing any badge, and no chevron on large rows) and `paused` (a pause dot, badge hidden), plus an optional BETA pill. `openFor` + `fallback` narrow `open` to a rollout slice that is matched against the viewer; `fallback: "hidden"` drops the tile (`resolveLaunch` in `lib/appConfig.ts`). A locked tile's tap opens `components/LaunchSheet.tsx`, a bottom sheet rendered by `AppModalHost` as a `kind: "launch"` request (`showLaunchSheet` in `lib/modal-host.ts`), with Notify me (`appConfigApi.notifyLaunch`, optimistic) or the paused alternative action. Soon taps are beaconed (`trackLockedTap`). **Route guard:** `guardRoute()` in `lib/launchGuard.ts` (called by `runTapAction` for routes, and in `AppShell`/`notifications.tsx` before pushing a push-notification or shared-link target) opens the sheet instead of a locked feature's screen. A route belongs to a feature when its path equals the feature route's path or sits under it, ignoring groups and the query (`launchForRoute`). `components/AppConfigSync.tsx` (in `AppShell`) mirrors config + viewer into the guard and refetches the config on sign-in/out. `isFeatureVisible` is true only when the feature is actually usable.
- **App settings** (`components/AppGate.tsx`, mounted in `AppShell`): maintenance mode blocks the app. Below `minVersion` the app is blocked with the store link. Below `latestVersion` a dismissible card shows once per version. None of this applies on web.

**How it loads:**
- Built-in defaults (today's layout) render first. Then the AsyncStorage cache (`period-buddy.app-config`), then a fresh fetch.
- The fetch is per viewer. It sends the session token attached by hand under `skipAuth`, so a stale token can never sign the user out from here, along with `X-Device-Id` (`lib/deviceId.ts`, a random id per install) and `X-Nura-Launch: 1`. Without that last header the backend hides every item that isn't plainly open, so older builds never show unfinished features.
- It refetches on foreground (≤ every 3 min), on Home's pull-to-refresh and on sign-in/out. A refresh asked for mid-fetch runs again once the fetch lands.
- Every failure is silent, and anything malformed or unknown falls back to the default.

**Adding a feature:** add it to `FEATURE_REGISTRY` here **and** to `constants/appCatalog.js` in the backend (same key, route, placement). A key only one side knows is ignored by the other.

### Data layer (`lib/api.ts`)

All backend access goes through one file: typed request helpers (`apiRequest`, `apiEnvelopeRequest`) plus one `xApi` object per domain (`authApi`, `cycleApi`, `habitsApi`, `forestApi`, `consultationApi`, `subscriptionApi`, `partnerApi`, `buddyApi`, `nominationsApi`, `communityApi`, `blogsApi`, `reelsApi`, `healthIssuesApi`, `wellbeingApi`, `questionAnswerApi`, `voiceAgentApi`, `uploadApi`, `documentApi`, `speechApi`, `reportApi`, `insightsApi`, `screeningApi`, `schemesApi`, `schemeApplicationsApi`, `genzApi`, `circlesApi`). Every response envelope is `{ data, error, message, ... }`; `apiRequest` unwraps `.data`, `apiEnvelopeRequest` returns the raw envelope (used for auth flows that need `token`/`user`/`isProfileComplete` alongside data). `healthApi` just wraps the `/health` liveness check.

- **Subscriptions / paywall** (`subscriptionApi`, `hooks/useSubscriptionAccess.ts`, `components/subscription/{LockedFeatureCard,PaywallModal,CouponField,FeatureGate}.tsx`, `app/(app)/subscription.tsx`): admins price individual features or bundles from the Content Studio (`period-buddy-be`'s `/api/admin/subscriptions/*`), and what's actually enforced server-side is driven entirely by that repo's `config/subscriptionRouteRegistry.js` — see its CLAUDE.md before assuming a given `hasAccess('key')` call here has a real backend gate behind it (nothing on the client can tell the difference between a wired key and an inert one; check the registry). `useSubscriptionAccess()` fetches `subscriptionApi.getMe()` once per mount (same shape as `useUserStats.ts`) and exposes `hasAccess('feature_key')`, plus `isLoading` — check `isLoading` before trusting a `false` from `hasAccess`, since it optimistically returns `true` until the first fetch resolves (so a locked screen never flashes its real content first). Three gating shapes are in use, pick per screen: (1) **action-level** — check `hasAccess(...)` right at the tap that starts the premium action (not deeper in the flow) and open `PaywallModal` when false, e.g. `CommunityScreen.tsx`'s new-post FAB, `symptom-checker.tsx`'s condition picker, `government-scheme-detail.tsx`'s Apply button, `qa-history.tsx`'s "+ New"/empty-state action, `partner.tsx`'s generate-invite-code button, `buddy-nomination.tsx`'s nominate action (checked *before* any optimistic state change, since that flow opens UI eagerly); (2) **whole-screen, hand-rolled** — `document-chat.tsx`, `checkin-call.tsx`, `documents.tsx`, `qa-history.tsx`, `government-scheme-detail.tsx` each inline the `locked`/`useEffect`/`LockedFeatureCard`/`PaywallModal` wiring directly (pre-dates the wrapper below); (3) **whole-screen, wrapped** — new screens should prefer `<FeatureGate featureKey="..." title="..." description="...">{content}</FeatureGate>` (`components/subscription/FeatureGate.tsx`) instead of reproducing shape (2)'s boilerplate — it renders `LockedFeatureCard`+`PaywallModal` in place of `children` while locked (so a locked screen's own data-fetching effects never even run) and the real content once unlocked; see `symptom-predictions.tsx` for the shape (split the screen into an inner `XContent()` component and wrap it). Whichever shape, also catch `isFeatureLockedError(err)` from the underlying API call as a fallback — the client-side check is only a cache, the server's registry-driven gate is the real one and can still 402 (a `402 FEATURE_LOCKED` response is parsed into `ApiError.kind === "featureLocked"` with a `.lock` payload carrying the feature's price and matching plans, so `PaywallModal` never needs a second fetch). Purchases run the same order→checkout→verify flow as `consultationApi` below, reusing `CashfreeCheckoutModal`/`CashfreeUpiCollectModal` as-is, with an optional coupon code (`CouponField`, shared between `PaywallModal` and `subscription.tsx`'s pricing grid — `subscriptionApi.applyCoupon()` previews a discount, `createOrder({..., couponCode})` redeems it; a 100%-off code returns `{free: true}` with no `orderId`/`keyId` at all, which both callers treat as "already unlocked, skip checkout entirely" via `finishFreeUnlock()`/the same inline handling in `subscription.tsx`). "My Subscription" (Profile → My Subscription) is the always-available pricing/purchase-history screen; `PaywallModal` is the reactive one shown when a lock is actually hit. `PaywallModal` itself is a `<Modal>`, and `CashfreeCheckoutModal`/`CashfreeUpiCollectModal` are also `<Modal>`s — two native Modals presenting at once is unreliable (the second one can silently fail to appear), so `PaywallModal` hides its own `visible` (`visible && !checkout`) the instant an order is created and only shows the checkout sheet; don't remove that guard when touching this file.

- `questionAnswerApi`'s `createSession`/`listSessions`/`getSession`/`sendSessionMessage`/`deleteSession` — `/api/questions/sessions*` (login-gated; `ask`/`getQuestions` above stay anonymous-friendly) — persisted Nura AI chat sessions, each optionally pinned to a topic (`lib/chatTopics.ts`'s `CHAT_TOPICS` — Periods & Cycle, Symptoms & Pain, Hygiene & Care, Mood & PMS, Sex & Intimacy, Nutrition & Wellness, and a catch-all Other/`general`; ids kept in sync with the backend's `utils/companionChat.js#CHAT_TOPICS`). Picking a topic chip scopes the session to just that topic, enforced two ways in `generateCompanionAnswer`: the system prompt (`topicScopeInstruction`) tells the model the restriction can't be lifted by anything the user says, and — since a model juggling "stay on topic" and "be helpful" in one breath will sometimes answer anyway by finding some loose thread back to the topic — a separate strict yes/no classification call (`isQueryOnTopic`) gates *both* the knowledge-base lookup and the AI call ahead of time; a NO short-circuits straight to a canned `offTopicReply()` without ever generating a real answer. "Other"/no topic skips this gate entirely and stays unscoped. The header's status line reflects the scope ("Focused on ‹topic›" vs "Private guidance online"). Picking a topic never shows a form: the chat opens scoped to it and its welcome swaps "Try asking" to that topic's `questions` (one tap sends). The `intake` definitions and `composeIntakeMessage()` in `lib/chatTopics.ts` are no longer rendered anywhere. "Sex & Intimacy" additionally sets `minAge: 18`, checked both client-side (`isTopicLocked()` dims the tile with a lock icon) and again in `createChatSession` (`isTopicAgeRestricted()`, backed by the asker's profile `dateOfBirth`) — the client check is UX only, the server call is what actually blocks a session; a 403 from `createSession` is shown as a chat message instead of silently falling through to the unscoped stateless fallback below. The system prompt itself may now ask **one** short clarifying question before answering when a question is genuinely too ambiguous, instead of always answering blind. **`app/(app)/qa.tsx` is not the landing screen**: opened bare (no `?voiceMode=1`, `?sessionId=`, or `?new=1`) it immediately `<Redirect>`s to `app/(app)/qa-history.tsx`, the Nura AI home: an "Ask anything" new-chat card, a topic grid and recent chats. Every plain entry point (the `nuraAi` hub tile, whose route is bare `/(app)/qa` in both repos' catalogs, tracker search, partner-view overview, ...) links to bare `/(app)/qa` and lands there first; keep the tile route on `/qa` (not `/qa-history`) so `launchForRoute` still guards the chat. Only the tab bar's center-avatar voice entry and the home's own taps (`?new=1[&topic=<id>]`, `?sessionId=`) skip straight into a chat; a `?topic=` chat hides the topic chips. A session is created lazily on the first message (never for idle browsing) and its id round-trips via `?sessionId=` so reopening a chat resumes it with full message history and the same topic scope; sending fails over to the stateless `ask()` + local knowledge base if the session call fails for a reason other than the age gate, same as before this feature existed, just without that turn being saved to history.
- `cycleApi.getSymptomPredictions()` — `GET /api/cycle/symptom-predictions`, per-symptom likelihood by cycle phase derived from the user's own logged history; powers `app/(app)/symptom-predictions.tsx`.
- `voiceAgentApi.checkinCall()` — `POST /api/voice-agent/checkin-call`, an on-demand outbound check-in call (Samvaad voice agent). **No longer called from the UI**: the "Call me now" button was removed, and `app/(app)/checkin-call.tsx` (Wellness & Support → Check-in Call) now only holds the phone number, the auto-call schedule and the call history. The number field saves via `authApi.updateProfile({ phone })` on blur and before the schedule is switched on (it can't be switched on without a number), since the backend always calls the number on the user's profile. Distinct from `voiceAgentApi.converse()` below, which is the in-app text/voice chat loop, not a real phone call. The same screen also has a recurring "auto check-in calls every cycle" toggle (`voiceAgentApi.get/saveCheckinCallSchedule()`, `GET`/`PUT /api/voice-agent/checkin-call/schedule`) — the actual firing happens server-side (`period-buddy-be`'s `utils/checkinCallScheduler.js`), ticked once a minute by that repo's `utils/inProcessScheduler.js` (in-process `setInterval`, the default — `ENABLE_IN_PROCESS_SCHEDULER=true`) or, for a multi-instance deployment, an external scheduler hitting `POST /api/voice-agent/checkin-call/scheduler-tick` with `ENABLE_IN_PROCESS_SCHEDULER=false` — **not** anything in this repo either way. If a saved schedule never actually calls, check that repo's README "Scheduled jobs" section first before assuming an app bug — the toggle can save successfully while `ENABLE_IN_PROCESS_SCHEDULER=false` with no external scheduler configured to replace it, in which case nothing is ever ticking (the manual "call me now" button still works in that state since it's a direct API call, not a scheduled one — don't take that as evidence the scheduler itself is fine).
- **Reminders & daily notifications**: the Cycle Settings sheet in `app/(app)/(dashboard)/tracker.tsx` already exposes `remindersEnabled`/`reminderDaysBefore`/`ovulationReminder`/`fertilityReminder` toggles (saved via `cycleApi`/`submitCycleSettings` onto `CycleSettings`), and `app/(app)/notifications.tsx` (bell icon, backed by `partnerApi.getNotifications()`/`markNotificationAsRead()`/`markAllNotificationsAsRead()` (header "Mark all read", `POST /api/partner/notifications/read-all`) — the in-app notification list lives under `/api/partner` for historical reasons, not a dedicated notification API) already renders every `AppNotification["type"]` including `period_reminder`/`ovulation_reminder`/`habit_reminder`, as day-grouped rows. Each row's icon/colour and optional collapsible banner image come from `lib/notificationIcons.ts` (`notificationIcon()`/`notificationImage()`): an admin-picked icon wins, else the type's own; `ADMIN_NOTIFICATION_ICONS` must stay in sync with the backend's `NOTIFICATION_ICONS` (`src/utils/notificationRoute.js`). What actually *creates* those reminder notifications is `period-buddy-be`'s `utils/dailyNotificationScheduler.js` — same external-scheduler pattern as the check-in call tick above, `POST /api/notifications/daily-tick` once a day — which reads those same CycleSettings toggles and also sends a once-daily "log today" nudge (`type: "system"`) when the user hasn't logged anything yet that day. Every `Notification` doc triggers its own push send automatically via its Mongoose post-save hook (FCM, `period-buddy-be`'s `utils/fcm.js`, skipped when the user's `notificationsEnabled` profile toggle is off) to whatever native FCM/APNs token (`getDevicePushTokenAsync`, not an Expo push token — the backend uses firebase-admin directly) `authApi.updateFcmToken()` last registered. `lib/notifications.ts` owns all of it: `setNotificationHandler` (foreground banners), the Android channel `ANDROID_CHANNEL_ID = 'default'` (small icon: `assets/images/brand/notification-icon.png`, a white-on-transparent silhouette as Android requires, tinted `#E8618F` via the `expo-notifications` plugin in `app.json`; icon changes need a new native build) (must match `utils/fcm.js`'s `android.notification.channelId`; created before the permission prompt, which Android 13+ requires), `requestNotificationPermissionAsync()` (permission only — used by onboarding's finish screen, `components/onboarding/OnboardingFlow.tsx`), `registerForPushNotificationsAsync()` (permission + token upload — only with a session; `auth-context.tsx` calls it on every launch/login and also subscribes `addPushTokenRefreshListener()` for FCM token rotation), and `enablePushOnDeviceAsync()` (Profile/partner Account notifications toggle switched on → re-asks or offers Settings). Logout (`POST /api/logout`) clears the token server-side, and uploading a token strips it from any other account that had it. Tap routing is `resolveNotificationTarget(data, isViewer)` in `lib/notifications.ts`, used both by `app/_layout.tsx` (push taps — queued until the navigator/auth are ready and the entry screens have redirected, then resolved with the signed-in role) and by rows in `app/(app)/notifications.tsx`: an explicit `data.route` (or `data.url`, validated to be an in-app path — admin broadcasts from the Content Studio's "Opens in the app" picker set this) wins, then `NOTIFICATION_TAP_ROUTES`/`PARTNER_VIEWER_TAP_ROUTES` by `type` (partner viewers get partner-view equivalents; the `system` daily nudge with `data.kind === "daily_nudge"` goes to the tracker), else the notifications list.
- `insightsApi.getDaily()` — `GET /api/insights/daily`, personalized daily hormone/mood/energy/skin insight plus exercise/nutrition/sleep/wellness suggestion lists; powers `app/(app)/insights.tsx`.
- `screeningApi` (`getQuestions`, `submitAssessment`, `getHistory`) — `/api/screening/*`, the PCOS/endometriosis/fibroid/thyroid symptom checker flow; powers `app/(app)/symptom-checker.tsx`.
- `schemesApi` / `schemeApplicationsApi` — `/api/schemes/*` and `/api/scheme-applications/*`, the Government Schemes & Benefits feature (women's reproductive & menstrual health schemes; Central + Rajasthan, state-independent architecture). Powers `app/(app)/government-schemes.tsx` (listing/search/category & Central-Rajasthan filters/recommended), `government-scheme-detail.tsx` (detail + eligibility checker + action buttons keyed by `actionType`: `APPLY`/`CHECK_ELIGIBILITY`/`FIND_FACILITY`/`LEARN_MORE`/`EXTERNAL_APPLICATION` — not every scheme is an "apply"), and `scheme-applications.tsx` (My Applications). Reached from Profile → Government Schemes & Benefits. Pure display/logic helpers live in `lib/schemeHelpers.ts` (unit-tested in `lib/__tests__/`). Eligibility never claims a guarantee — only "You may be eligible". A `FIND_FACILITY` scheme's primary CTA opens a Google Maps government-hospital search (`schemeHelpers.governmentHospitalMapsUrl(user.state)`) — **not** the scheme's `officialUrl`, which is an info page and stays on the secondary "Official Website" button. Admins create/edit/delete schemes from the separate `period-buddy-content` web portal (Content Studio), not the mobile app; the app is read-only over `/api/schemes/*`.
- `app/(app)/graphs-reports.tsx` (Profile → Graphs & Reports) is a colorful gradient-card dashboard — Cycle length (last 3 lengths from `cycleApi.getPredictions().analyticsData` as proportional pill bars), Weight and Basal body temperature (latest logged value, derived client-side from `cycleApi.getMonthLogs()` over the last 3 months — there's no backend aggregate for these two yet), and Water intake / Sleep (90-day averages from `reportApi.getHealthReport(...).cycle.averages`) — plus a Reports section linking to `symptom-report.tsx` and to Documents' existing "Download doctor report" flow (`router.push({ pathname: "/documents", params: { openReport: "1" } })`, which `documents.tsx` reads via `useLocalSearchParams` to auto-open its report modal pre-filled to the last 90 days). `app/(app)/symptom-report.tsx` renders `reportApi.getHealthReport(...).cycle`'s `symptomCounts`/`moodCounts`/`flowCounts` as ranked bar lists plus the sleep/water/stress averages — a read-only "review your symptoms and cycle" view, distinct from the downloadable PDF.

- `lib/cycle.ts` is the canonical source for the `CyclePhase` type and `getCyclePhase(cycleDay, periodLength, cycleLength)` — import it instead of re-deriving cycle phase locally (tracker, forest, symptom predictions, and `DayEntry.phase` in `lib/api.ts` all use it). Likewise `getCycleDay` in `lib/cycleCalendar.ts` is the one day-of-cycle count (tracker, Home's week strip, Calendar screen); it rounds the gap between local midnights so a daylight-saving change can't shift days (`lib/__tests__/cycleCalendar.test.ts`). Day keys are always local (`getDateKey`), never `toISOString().slice(0, 10)`, which is the UTC date. A failed day-log save calls `alertLogNotSaved` (`lib/alert.ts`) instead of being swallowed.
- **Cross-screen refresh (`lib/data-sync.ts`, `hooks/useDataRefresh.ts`)**: dashboard tabs and any screen lower in the stack stay mounted, so a one-time fetch-on-mount goes stale when another screen writes. `apiEnvelopeRequest` calls `emitMutation()` after every successful non-GET, and `topicsForMutation()` maps the endpoint to `DataTopic`s (`cycle`, `dashboard`, `profile`, `subscription`, `notifications`, `qaSessions`, `schemeApplications`, `documents`, `partner`, ...; unit-tested in `lib/__tests__/data-sync.test.ts`) — so writes need no manual wiring, but a **new endpoint that changes data another screen shows must be added to `MUTATION_TOPICS`** (requests that bypass the helper, like `documentApi.upload`, call `emitDataChange` by hand; so does a foreground push, via `app/_layout.tsx`). Screens subscribe with `useDataRefresh(topics, cb)` — `cb` runs (debounced) immediately if the screen is focused, otherwise once on its next focus, with `{ whileFocused }` so a screen can skip refetching over its own writes (profile, partner) or do a lighter refetch (tracker) — or with `useAsyncLoad(fetcher, deps, { refreshOn })`. Callbacks must refetch silently (no loader, keep data on failure). `useUserStats`/`useSubscriptionAccess` also drop their 60s module cache on `dashboard`/`subscription`, which is what makes `FeatureGate` unlock after a purchase.
- `hooks/useUserStats.ts` is the canonical source for streak/wallet numbers (`{ streakCount, walletBalance }`); it fetches the dashboard once and syncs it into auth-context. Screens should consume this hook instead of reading `user.streakCount`/`user.walletBalance`/`user.tokenEarned` directly, so streak/points never drift between screens.
- Auth token is stored in AsyncStorage under `period-buddy.auth-session` (`AUTH_SESSION_KEY`) and attached as `Authorization: Bearer` automatically; pass `skipAuth: true` for public endpoints.
- `AuthUser.partnerRole` is resolved client-side after login (`lib/auth.ts#connectPartnerAndResolveRoute`) and never comes back on server user objects, so `auth-context.tsx#updateUser` keeps the existing role unless the caller passes one explicitly (`null` included, as on partner disconnect) — otherwise passing a fresh `authApi.updateProfile()` result would drop it and the partner-view layout guard would bounce a viewer into the owner dashboard. Because the role otherwise lives only on-device, `AuthProvider` re-syncs it from `partnerApi.getProfile()` (`syncPartnerRole`) on every launch/login and app foreground, and `PartnerViewStateProvider.refreshProfile()` pushes the fresh profile's role in too — so an owner-side disconnect (server sets the viewer's role to `null`) or a failed role lookup at login self-corrects via the layout guards. A sequence counter (`roleWriteSeq`) drops sync results that started before a sign-in/out or explicit role write, so the post-login sync can't race `connectPartner()` and overwrite the fresh `viewer` role. `DELETE /api/partner/disconnect` also emits a `partner_disconnected` WebSocket event to both sides' personal `user_<id>` rooms (plus a push to the other side): the partner view re-fetches on it (→ role sync → guard redirect) and the owner's `(app)/partner.tsx` reloads its profile, so either side ending the connection updates the other immediately.
- A 401 triggers a global `onUnauthorized` handler registered by `AuthProvider`, which clears the local session — don't hand-roll 401 handling per screen. It only fires when the token the request carried is still the session's, so a slow request from before a logout/login can't sign the new account out. When the account changes (`signIn` with a different user id, or `signOut`), `AuthProvider` clears per-account data held outside React state: it emits the `dashboard`/`subscription` topics (dropping `useUserStats`/`useSubscriptionAccess`'s 60s caches) and `clearStoredAppState()` (saved/reported posts persisted by `components/AppState.tsx`). Day logs/notes in `AppState` are an in-session overlay only and are never persisted on any platform: every save also goes to the server, which is the source of truth. Add any new module-level per-user cache to that list. A response with `code: "ACCOUNT_SUSPENDED"` (403 from login/Google sign-in, 401 mid-session — see `period-buddy-be`'s `utils/accountStatus.js`) becomes `ApiError.kind === "accountSuspended"` (`isAccountSuspendedError()`); on an authenticated request it calls `onUnauthorized("suspended")`, and `AuthProvider` signs out and shows one "Account suspended" alert. On the login screens the server's message just shows in the existing error banner.
- Every request is aborted after `DEFAULT_TIMEOUT_MS` (20s; override per-call with `timeoutMs`, `0` disables) and every failure throws a typed `ApiError` carrying `kind` (`network`/`timeout`/`server`/`notFound`/`unauthorized`/`unknown`) and `status`. Use the exported `isNetworkError(err)` and `getFriendlyErrorMessage(err)` helpers to branch on connectivity vs. show copy — don't string-match `.message`. `useAsyncLoad` already exposes an `offline` boolean derived from these; `LoadingErrorState` and `EmptyState` take an `offline`/`wifi-off` variant.
- Several types carry `@deprecated` fields kept for backend backward-compat (e.g. `tokenEarned` → `walletBalance`, `likes` → `likeCount`, `views`/`viewsCount` → `viewCount`) — use the non-deprecated field in new code.
- File uploads (`uploadApi.uploadImage`, `documentApi.upload`, `speechApi.transcribe`) bypass the JSON helpers and build `FormData` directly, with a web-vs-native branch (web needs a real `Blob`, native uses the RN `{uri,name,type}` shape).
- Realtime (buddy chat, video call signaling) goes over a WebSocket at `WS_BASE_URL` — construct the URL via `getWebSocketUrl()` so the auth token query param is attached consistently.

### Sharing & deep links

`lib/share.ts` (`shareWithAppLink`, used via `components/AppState.tsx`'s `sharePost` or directly) is the one way to share anything that should reopen in-app: it wraps an in-app path (e.g. `"community?postId=abc123"`) into `https://thenura.care/app?deeplink=<path>`. Don't call `Share.share` directly for shareable in-app content. Current share points and their deeplinks: blog detail (`blogs?slug=`), reel cards in blogs and the Share button on each reel in `reels.tsx` (`reels?reelId=`), community posts (`community?postId=`), government scheme detail header (`government-scheme-detail?id=<slug>`), partner invite (`partner-connect?code=`), symptom checker results (`symptom-checker`), Bestie Circle invites (`circles?code=`), and the Gen Z share cards' text fallback (`wrapped`, `era`, `badges`). **Every deeplink route's first path segment must be in `lib/deeplink.ts#SHAREABLE_ROUTES`**, or incoming links to it are ignored (the app just opens). Target screens read their id with `useLocalSearchParams` and open the item themselves after mount (blogs → article modal, community → comments sheet, reels → fetches that reel via `getReelById` and pins it first/playing, scheme detail → loads by `id`, partner-connect → prefilled code).

Incoming links: `app/+native-intent.tsx#redirectSystemPath` (expo-router's pre-routing hook, cold start and warm) runs every URL through `lib/deeplink.ts#resolveDeepLink`, which recognizes both `https://thenura.care/app?deeplink=<path>` (Android App Link) and `thenura://<route>?...` for shareable routes; anything else (OAuth redirects, dev-client URLs) passes through untouched. For ours it *queues* the target in `lib/deeplink.ts` and returns `/` (cold) or `""` (warm, = don't navigate), so expo-router never lands on the unmatched `/app` route. `AppShell` in `app/_layout.tsx` consumes the queue (`useSyncExternalStore`) and `router.push`es it once the navigator is ready, the user is signed in, and the entry screens (`ENTRY_PATHS`) have redirected to the dashboard — so Back returns to the dashboard, and a logged-out user's link stays queued (in memory) until they log in. `PUBLIC_DEEP_LINK_PATHS` (just `/partner-connect`) opens without waiting for login. `/community` is rewritten to `/forum` for partner viewers. Every push adds an `openedAt` timestamp param so an already-mounted screen (the community tab) re-opens the item when the same link is tapped twice. Don't add a separate `Linking` listener for these — that was the old duplicate handling.

Android App Links: `app.json`'s `android.intentFilters` (https, `thenura.care`, `pathPrefix: /app`, `autoVerify: true`) needs `https://thenura.care/.well-known/assetlinks.json` (marketing site repo `The-Nura-Marketing-Website/public/.well-known/`, served as JSON by its `vercel.json`) to list the **Play Console App signing key SHA-256** — until that fingerprint is filled in and deployed, Android won't verify and the https link opens the browser instead. The browser fallback is that repo's `src/pages/AppRedirect.jsx` (`/app` route): on Android it navigates to `intent://<deeplink>#Intent;scheme=thenura;package=com.uvin124.thenura;S.browser_fallback_url=<Play Store with referrer=deeplink=...>;end` (works in Chrome and most in-app browsers; also offered as a button since some webviews need a real tap), iOS/desktop get buttons. The Play Store `referrer` is set but not read by the app yet (no install-referrer library, so no deferred deep link after a fresh install). `ios.associatedDomains` + `apple-app-site-association` (placeholder Team ID) are there for when iOS ships. Intent filter / scheme changes need a new native build; test with `adb shell am start -a android.intent.action.VIEW -d "<url>"`.

### Styling

NativeWind (Tailwind for RN) via `tailwind.config.js` / `global.css`, plus `components/theme.tsx` (light/dark, hydrated before first paint) and `components/ui-tokens.ts` for shared design tokens (including `getSeverityColor` for danger/warning/success by numeric threshold). `ThemeColors` has two extra category accents beyond the rose/lavender/mint trio — `sky` (blue) and `gold` — added for the day-log modal and Graphs & Reports; `getSoftTints`/`getLogCategoryTints` (`ui-tokens.ts`) expose them alongside the rest as pale-bg/solid-fg pairs.

**Fonts:** exactly two typefaces app-wide — Manrope (`fonts.heading`/`fonts.body`) for all headings and body copy, IBM Plex Mono (`fonts.mono`/`fonts.monoSemiBold`) for numeric/code-like content (streaks, OTPs, stats). IBM Plex Mono and the icon fonts (`Ionicons`/`Feather`/`MaterialCommunityIcons`, preloaded behind the splash so icons don't pop in late — add any new `@expo/vector-icons` family there too) load in `app/_layout.tsx` via `useFonts`. **Manrope is embedded natively, not loaded at runtime:** the `expo-font` plugin in `app.json` builds one `Manrope` family from the static `assets/fonts/Manrope_<weight>.ttf` files (300–800), so plain `fontWeight` picks the right file. Android can't pick weights from a variable font (it renders the ExtraLight default), and a runtime font with the same name would replace the family, so `Manrope-Variable.ttf` loads at runtime **only on web**. Font changes need a new native build. Don't add other font families without updating `ThemeFonts` there too. Text without an explicit `fontFamily` still gets Manrope from `lib/react-native-shim.tsx`: `metro.config.js` points app code's `react-native` import at it (`node_modules` keeps the real one), and its `Text`/`TextInput` add `fontFamily: "Manrope"` before the caller's style. `Text.defaultProps` can't do this, since React 19 ignores `defaultProps` on function components. The shim is written as JSX so NativeWind still handles `className`.

**NativeWind gotchas (only obvious on a real build):** `className` works only on components NativeWind wraps (RN core, safe-area `SafeAreaView`, and anything registered with `cssInterop` at the top of `app/_layout.tsx`, currently `LinearGradient`); on anything else it is silently ignored, so register new third-party components there. A function style on `Pressable` (`style={({ pressed }) => ...}`) gets dropped in release builds: use `components/PressableFeedback.tsx` (same API) for pressed-state styles.

### Shared screen scaffolding

**Look and feel follows Home.** `components/ScreenHeader.tsx` exports the shared chrome: `ScreenHeader` (back button + 20/800 title + optional subtitle/right actions), `TabHeader` (22/800, for tab roots), `HeaderIconButton` (38px round surface button with the soft shadow, same as Home's bell) and `SectionHeader` (Home's colour bar + 14.5/800 title + optional "See all"). Use them instead of hand-rolling a header. Text floor: helper/subtext is at least 13px (`text-xs` is remapped to 13px in `tailwind.config.js`), uppercase labels at least 11.5px; `font-black` renders as 800 to match Home. Keep helper copy to one short line. Don't add descriptions to self-explanatory settings (period length, reminder toggles…). **Layout:** 24px screen gutter; bottom sheets pad by `useSafeAreaInsets().bottom`, never a fixed number; screens/sheets with text inputs use `KeyboardAvoidingView` or `automaticallyAdjustKeyboardInsets`. `app/_layout.tsx` centres every screen in a column at most `MAX_CONTENT_WIDTH` (640, `lib/layout.ts`) wide for tablets, so size carousels/pagers/grids with `useContentWidth()`, not the raw window width. The tracker shows `TrackerBodySkeleton` until dashboard + predictions load, instead of default values. **Don't repeat Home on other tabs:** the tracker deliberately has no greeting or stats row (Home/Profile have them); it's a `TabHeader`, this week's strip under it (same day cells as the calendar, tap a day to log it), the read-only cycle ring card with "Log period" / "Symptoms" buttons, and the calendar (tap a day to log it). `components/ScreenHeader.tsx` and `components/LoadingErrorState.tsx` (full-screen loading/error-with-retry) cover the common shape of simple detail screens; its default loading state is the branded `components/Loader.tsx` (bear mascot inside a pulsing/rotating themed ring — use it, or `<Loader fullscreen />`, instead of a bare `ActivityIndicator` for page-level waits); `hooks/useAsyncLoad.ts` collapses the load-on-mount + pull-to-refresh + error-state boilerplate around a single fetcher. **Paged lists**: `hooks/usePaginatedList.ts` (`fetchPage(page) → { items, hasMore }`; returns `items`/`setItems`/`loading`/`refreshing`/`error`/`offline`/`hasMore`/`loadingMore`/`loadMore`/`reload`, dedupes by `_id`/`getKey`, and its `refreshOn` background refresh merges page 1 over the top instead of collapsing opened pages) plus `components/LoadMoreButton.tsx` ("Show more") — used by notifications, qa-history; documents and the older blogs/government-schemes/scheme-applications screens hand-roll the same page/hasMore/loadingMore shape. Mutate rows in place with `setItems` (e.g. mark read, delete) rather than `reload()`, which would collapse the list back to page 1. `hasMorePages(pagination)` (`lib/api.ts`) is the one "is there another page" check. Endpoints that used to return bare arrays expose paging on the *envelope* (`partnerApi.getNotificationsPage`, `questionAnswerApi.listSessionsPage` go through `apiEnvelopeRequest`, since `apiRequest` drops everything but `data`); see `period-buddy-be`'s CLAUDE.md "Pagination". Prefer these over re-implementing the same screen shell.

A full screen shared verbatim across route groups (not just scaffolding) lives in `components/screens/` — e.g. `CommunityScreen.tsx`, re-exported by both `(dashboard)/community.tsx` and `(partner-view)/forum.tsx` — so the two roles can never visually drift apart on a screen that should look identical for both.

### Tracker calendar (`app/(app)/(dashboard)/tracker.tsx`)

**One day design everywhere:** `components/CycleCalendar.tsx#CalendarDayCell` draws every calendar day (Tracker pager via its `height` prop, Calendar screen month view), with `CalendarLegend` explaining it (five fixed columns, each a mini day chip over its label, so it stays one row at any width) — logged period solid, predicted period dashed ring, past unlogged period soft tint, fertile lavender wash, ovulation egg, today primary ring, a dot for days with a log. Don't add per-screen day styling. The ring in the tracker's cycle card (`CycleRing`) is read-only: phase label, one big value, one fertility line.

The calendar card still renders all 12 months of the selected year stacked and scrollable (`calendarMonths`), but the initial landing on the current month is instant, not animated: the month list stays hidden (`calendarRevealAnim`, opacity 0), and its container clamped to `CALENDAR_LOADING_HEIGHT` with `overflow: hidden` (a `Loader` sits over that clamped area), until the first `scrollTo({ animated: false })` — driven by `monthLayouts` from each month's `onLayout` — has landed on `selectedMonthIndex` (initialized to today), then fades in already positioned there, so opening the tracker never shows a visible "scrolling to current month" motion. `hasInitialScrolled` (a ref, claimed the instant the jump is scheduled — not after it runs, so a second `onLayout` arriving in between can't schedule a duplicate one) gates that one-time instant jump. Expanding the container to its true height (`setIsCalendarRevealed(true)`) and calling `scrollTo` are deliberately **not** in the same tick: the container's expansion is itself a state update the native/DOM side hasn't re-measured yet, so a same-tick `scrollTo` targets a y position beyond what the still-clamped content currently allows and silently comes up short (reproduces identically on native and web — this bit it before, see git blame if it regresses again). A nested double `requestAnimationFrame` after `setIsCalendarRevealed(true)` waits for that re-layout to actually land (one frame for React's re-render, one for the paint) before scrolling and starting the fade. Every later month change (chevrons, the "Today" pill shown once you've navigated away from the current month) scrolls smoothly instead, since by then the container is already at full height and it's a deliberate, visible action. The 4-phase legend (`phaseLegendRow`) is defined once and rendered twice — inline at the top of the calendar card, and as a floating copy in the fixed header (`showFloatingLegend`, compares live page scroll offset `pageScrollY` against the calendar card's measured top `calendarSectionY`) that takes over once the in-card legend has scrolled out of view, so the phase colors stay reachable without scrolling back to the top.

### Wellness Forest (`app/(app)/forest.tsx`)
