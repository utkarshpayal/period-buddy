## Working rules (all Nura repos)

The full flow is in docs/WORKFLOW.md. The guard hook in `.claude/hooks/guard.mjs` enforces the 🔒 rules.

1. **Branch first:** `git switch -c <type>/<name> origin/staging` (`feat`, `fix`, `chore`, `docs`, `refactor`). 🔒 No commits on `main`.
2. 🔒 **Never push to `main` or force-push `main`/`staging`.** Push your branch only when asked, then a PR goes to `staging`. `main` changes only through a reviewed `staging` → `main` release PR, or a hotfix PR (branch from `origin/main`, then merge `main` back into `staging`).
3. **Leave other people's uncommitted changes alone.** Don't commit, stash, reset or discard them; use a `git worktree` from `origin/staging` instead.
4. 🔒 **Secrets:** never read, print, copy or commit `.env*` (except `.env.example`), keystores or credentials, or read secret values from AWS. Name the key and let the person set the value. A new env var goes in `.env.example` and in every environment (prod and staging).
5. 🔒 **Production is opt-in:** read-only checks are fine. Changing AWS, Vercel, EAS production or live data needs the person's explicit go-ahead, and the hook asks each time. Do it on staging first.
6. **Verify before done:** run `npm run lint` and `npm test`, the same checks CI runs. Report failures with their output.
7. **Docs in the same change:** keep this file, the API docs and the cross-repo contracts (WORKFLOW.md §7) in sync with the code.
8. **Stay in scope**, and list other problems you spot instead of fixing them unasked. Work inline: no subagents unless asked.
9. **Commits and PR titles:** `<type>(<scope>): <summary>`, imperative, lowercase, ≤ 72 characters. Fill in the PR template.

## Keeping this file current

This file must stay in sync with the codebase. After any change that affects architecture, routes, API surface (`lib/api/`), providers, or commands below, update the relevant section in the same session — don't wait to be asked.

## Versioning

The version follows the **`staging` branch** (where feature branches are merged; `git show origin/staging:package.json`): a branch carries staging's version and is not bumped per change while it's unmerged. Bump only when asked. Keep these in sync: `app.json` → `expo.version`, `package.json` → `version`, and `package-lock.json`'s top-level `version` and `packages[""].version`. The Android `versionCode` is separate: EAS manages it remotely (`appVersionSource: remote`, `autoIncrement` on `production`), so don't touch it.

## Commands

```bash
npm install              # install deps
npx expo start            # start dev server (scan QR / press a,i,w)
npm run android            # start + open Android
npm run ios                # start + open iOS
npm run web                 # start + open web
npm run lint                 # expo lint (eslint.config.js, eslint-config-expo)
```

`npm test` runs the unit tests in `lib/__tests__/*.test.ts` with Node's built-in runner (`node:test` + `node:assert`, TypeScript via `sucrase/register`) — not Jest. There is no `build` script — production builds go through EAS:

```bash
eas build --platform android --profile preview
eas build --platform ios --profile preview_ios
```

The backend is picked by `EXPO_PUBLIC_APP_ENV` (`prod` | `stage`), which maps to `app.json`'s `extra.apiBaseUrls` (`https://www.backend.thenura.care` / `https://stage.backend.thenura.care`); `EXPO_PUBLIC_API_BASE_URL`, if set, overrides it with any URL (e.g. a local backend). EAS profiles in `eas.json` bake the toggle in at build time: `base` (preview/development) is `stage`, `production` is `prod`. In `__DEV__` with neither env var, `lib/api/` derives the API host from the Expo dev server's `hostUri` on port 5001 (`LOCAL_DEV_API_PORT`; on web it's always `http://localhost:5001`); a release build with neither uses prod. The four Google OAuth client IDs work the same way: `EXPO_PUBLIC_GOOGLE_*_CLIENT_ID` wins, else `extra.googleClientIds` (public IDs; must match the backend's `GOOGLE_*_CLIENT_ID`), so a build or dev server without `.env` still has working Google sign-in.

App identity/config lives in `app.json` (source of truth; Android builds both `armeabi-v7a` and `arm64-v8a` so 32-bit budget phones can install it; the adaptive launcher icon is `assets/images/brand/adaptive-foreground.png` (logo scaled into the 66% safe zone, on white) plus `adaptive-monochrome.png` for Android 13+ themed icons — regenerate both from `app-icon.png` if the logo changes) plus a thin `app.config.js` wrapper that only overrides `android.googleServicesFile` / `ios.googleServicesFile`. Those two files (`assets/google-services.json`, `assets/GoogleService-Info.plist`) are Firebase *client* configs and are git-tracked on purpose (their keys ship in every binary anyway; see `.gitignore`), so `app.json`'s paths work in EAS cloud builds. `app.config.js` still lets `process.env.GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICES_INFO_PLIST` (EAS **file**-type environment variables, set per-environment via `eas env:set --type file`, currently populated for `development`/`preview`/`production`) override them, falling back to the tracked files when those env vars aren't set. `eas.json`'s `preview_android`/`preview_ios` profiles don't match a canonical EAS environment name by profile name alone, so they carry an explicit `"environment": "preview"` to pull the same vars; `development`/`preview`/`production` profiles match by name automatically. Local Android signing (`credentialsSource: "local"` in most `eas.json` profiles) needs a gitignored `credentials.json` + `credentials/android/keystore.jks` in the project root — not committed, restore from the EAS keystore backup if missing (`eas credentials` can regenerate one only as a last resort, since Play Store update-signing requires the *same* key).

## Architecture

This is an Expo Router (v6, file-based routing) app — **frontend only**; the backend (`period-buddy-be`) lives in a separate repo/service and is consumed entirely through `lib/api/`.

### Provider stack (`app/_layout.tsx`)

```
ThemeProvider (components/theme.tsx)
  GenZModeProvider (components/genz-mode.tsx)  — purely cosmetic label-swap toggle (Profile → Preferences & Settings), AsyncStorage-persisted, no backend/auth dependency
    AuthProvider (components/auth-context.tsx)  — hydrates session from AsyncStorage before children render
      AppLockProvider (components/AppLock.tsx)  — PIN/biometric app lock, renders AppLockScreen overlay
        AppShell — waits for theme hydration, hides splash screen, renders <Stack/> + AppModalHost
```

`app/(app)/_layout.tsx` additionally wraps its subtree in `AppStateProvider` (`components/AppState.tsx`) and `HomeLayoutProvider` (`components/home-layout.tsx`, each person's own Home layout).

Modals are centralized: `components/modals/AppModalHost.tsx` is a single host rendered at the root, driven by `lib/modal-host.ts`. Prefer routing new modal UI through that host instead of ad hoc `Modal` components. A component that renders its own `<Modal>` and can raise alerts while open mounts `<AppModalHost inline />` as that Modal's last child (only while visible); hosts stack, newest wins, so its alerts draw on top of it instead of behind it (see `DayDetailsModal`). A `<Modal>` that shows health, account or payment details and doesn't mount that host gets `<AppLockCover />` (`components/AppLockScreen.tsx`) as its last child instead, so the App Lock covers the sheet without closing it (native Modals draw above the root lock screen); the host already includes it.

### Route groups (`app/`)

- `app/index.tsx` — logged-out welcome: 3 swipeable value slides (each a small icon in a tinted halo; auto-advance every 4s, looping, paused while dragging or covered by another screen, off with reduced motion), then "Get started" (→ signup), "I already have an account" (→ login) and the partner-invite link. There is no first-launch permissions screen: notifications are asked on onboarding's finish screen, microphone and (iOS only) photos the first time a feature needs them.
- `(tabs)/` — pre-auth flow: `login`, `signup` (Google first, then first name + email + password with a live rule checklist from `lib/password.ts`, which mirrors the backend's `validatePasswordStrength`; last name is optional and not asked; consent is the "By continuing…" line linking thenura.care/terms and /privacy), `partner-connect`.
- **First-run setup** (`components/onboarding/OnboardingFlow.tsx`, pure logic in `lib/onboarding.ts`, unit-tested): shown by `(dashboard)/_layout.tsx` while `user.isProfileComplete === false`. One question per screen: goals → last period start (month grid, or "I don't remember" → rough ranges) → period length → cycle length (steppers, "Not sure" uses 5/28) → birthday (`components/BirthdayInput.tsx`, typed DD/MM/YYYY boxes, 13+) → a finish screen with the first prediction and the notification soft-ask. Answers are saved per user in AsyncStorage so a killed app resumes where it left off. The last question saves the profile and cycle settings together; a failure shows inline with retry. `auth-context` holds off push registration until setup is done (except for partner viewers, who never see it). Phone and photo are not asked here: they're optional and live in `(app)/edit-profile.tsx` (Profile → Edit profile, plus a "Complete your profile" card while either is missing).
- `(app)/` — authenticated app, one screen per top-level feature (tracker, habits, forest, consultation, community, blogs, reels, documents, document-chat, qa, qa-history, checkin-call, health-issues, hygiene, sexual-wellbeing, buddy-nomination, partner, app-lock, government-schemes, government-scheme-detail, scheme-applications, graphs-reports, symptom-report, ...), plus three "hub" screens — `care-hub`, `wellness-hub`, `explore-hub` — that each group several of those features behind one Home entry point (see below).
  - `(app)/(dashboard)/` — the main tab bar: `home`, `tracker`, `community`, `profile`.
    - `home.tsx` is intentionally short: greeting, stat pills, week strip, cycle-phase hero card, quick actions, an Insights carousel (See all → `predictions`), then a single "More for you" section: three rows in one `components/ListGroup.tsx` card (`ListGroup` + `ListRow`, the app's grouped-list look) — `Care & Insights` → `(app)/care-hub.tsx` (predictions, daily insights, symptom trends/checker, graphs & reports, book-a-consult CTA), `Wellness & Support` → `(app)/wellness-hub.tsx` (health concerns, Nura AI, hygiene, sexual wellbeing, check-in call), `Explore` → `(app)/explore-hub.tsx` (forest, blogs, videos, partner sync, habits, buddy nomination). Add a new lightweight/browse destination to the matching hub screen, not to Home directly — Home should stay a short dashboard, not grow back into a long list of tiles.
  - `(app)/(partner-view)/` — shown when the signed-in user is a connected partner "viewer" rather than the data owner (see `AuthUser.partnerRole`). Has its own floating tab bar (`_layout.tsx`) matching `(dashboard)/_layout.tsx`'s look exactly (both use `components/TabBarItem.tsx`'s `TabBarItem` and `CenterAvatarTabIcon`): `overview` (read-only shared overview: a `GradientCard` cycle card with day, phase in neutral third-person words (`lib/partnerView.ts#PARTNER_PHASE_COPY`, unit-tested), next period and fertile window; "How to help today"; "Recent days" as readable tags (`logTags`, never raw values like `moodSwings`), 3 days then Show all; "Ways to help" collapsed to 2 do's / 2 don'ts; "Learn together" as a `ListGroup` with Talk to a gynaecologist first. Chat lives only in the Chat tab; don't add chat shortcuts here), `chat` (owner↔partner messaging), `voice` (center avatar, same mic-permission-gated voice assistant), `forum` (identical UI to the owner's — both re-export `components/screens/CommunityScreen.tsx`), `account` (partner's own account: notifications, app lock, privacy & security, Help & support → `/support-tickets`, disconnect, logout) — a code comment in `_layout.tsx` notes these names are deliberately distinct from the dashboard's tab names. `overview`'s notification bell pushes to the shared `(app)/notifications.tsx` screen — the same one the owner dashboard's bell opens — instead of its own bottom-sheet drawer, so the two roles see byte-identical notification UI; on focus it re-syncs `usePartnerViewState()`'s notifications so the bell's unread badge stays accurate after reading/marking things there. Cross-tab state (profile, notifications, live chat messages, the one WebSocket connection) lives in `components/partner-view-state.tsx`'s `PartnerViewStateProvider`/`usePartnerViewState()`, since Tabs screens are siblings and would otherwise each re-fetch/reconnect independently.

### Security & privacy

- **Session storage** (`lib/sessionStore.ts`): the token lives in the OS keystore (`expo-secure-store`, this device only, not backed up); only the non-secret profile is in AsyncStorage under `AUTH_SESSION_KEY`. Always go through `saveSession` / `loadSession` / `clearSession`, never AsyncStorage directly. Sessions are revocable server-side, so any request can come back 401 "You have been signed out".
- **Privacy screen** (`app/(app)/privacy.tsx`, Profile → Data privacy & security): AI consent switch (`authApi.setAiConsent`; AI endpoints answer 403 `AI_CONSENT_REQUIRED` when it's off), Download my data (`lib/privacyExport.ts`), signed-in devices with per-device sign-out and sign out everywhere.
- **Medical documents** are private: `fileUrl` is a 10-minute signed link, so `documents.tsx` fetches the document again on open. PDFs open in the iOS WebView or, on Android, the phone's own PDF app via a cached copy that's deleted afterwards. Never hand a document link to an online viewer.
- API requests send `X-App-Version` and `X-Timezone-Offset` (the backend's `clientTodayKey`: cycle day, phase and "days until" count from the phone's local today, not server UTC), and `/api/auth/*` also `X-Device-Id`, so the backend can list devices.
- **Privacy screen settings**: besides AI consent, `authApi.setPrivacySettings` saves `hideNotificationDetails` (neutral lock-screen push text), `newSignInAlerts` (new-device email) and `aiChatRetentionDays` (auto-delete old AI chats) on the account. Two more switches are per phone (`lib/screenPrivacy.ts`, AsyncStorage): "Block screenshots" (`useSecureScreen(key, active?)` on focus, via `expo-screen-capture`; used by every screen with personal health or account details: documents, qa, qa-history, document-chat, tracker, calendar, home, predictions, insights, symptom checker/predictions/report, graphs-reports, wrapped, era, forest, habits, circles, notifications, edit-profile, checkin-call, scheme-applications, consultation, partner, partner-view chat/overview, the buddy chat and `DayDetailsModal`; add it to any new screen showing health details) and "Blur in app switcher" (iOS, `ScreenPrivacySync` in `AppShell`). Builds without the native module skip both. **Needs a new native build.**
- **No photo/video storage permission on Android** (Play's Photo and Video Permissions policy): `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` are in `app.json`'s `android.blockedPermissions` (`expo-screen-capture`'s manifest would otherwise add `READ_MEDIA_IMAGES` for its screenshot listener, which the app doesn't use). `expo-image-picker` opens the system photo picker, which needs no permission, so pick photos/videos through `lib/photoAccess.ts#requestPhotoLibraryAccess` (asks on iOS only) + `launchImageLibraryAsync`; never call `requestMediaLibraryPermissionsAsync` directly or add `expo-media-library`. Manifest changes need a new native build.
- **Health data on the phone** goes through `lib/secureStorage.ts` (OS keystore, moves old AsyncStorage values on first read), not AsyncStorage. The onboarding draft uses it; keep new health-related caches there too.
- **Prescriptions**: the backend renders the printable page (`GET /api/consultation/:id/prescription` → `{ html, fileName, number }`), so the app never builds prescription HTML itself. `components/PrescriptionCard.tsx` (top of a consultation chat: medicines at a glance from `consultation.rx`, or the text of older ones) opens `PrescriptionViewer.tsx` (the page in `PrescriptionDocumentView`, a script-less WebView; `.web.tsx` is a sandboxed iframe) and calls `lib/prescriptionPdf.ts#prescriptionAction` to save a PDF (share sheet) or print (`Print.printAsync`; on web a print window, opened before any await).
- **Temporary health files** (a PDF handed to the PDF app, the data export) are deleted later by `lib/tempFiles.ts#cleanupTempFiles` (preview close, prescription viewer close, Documents/Privacy/Consultation screen open), never right after `shareAsync`: on Android that returns before the other app has read the file. New files of this kind need a prefix in `TEMP_PREFIXES`.
- **No tracking of under-18s** (`lib/analyticsConsent.ts`, set by `AppConfigSync` from the profile birthday): `trackUse` and `appConfigApi.trackLockedTap`/`trackBannerClick`/`trackBannerImpressions` send nothing for them. Any new analytics beacon must check `analyticsAllowed()`.
- **Dependency audit** in CI is `audit-ci` with `audit-ci.jsonc` (reviewed exceptions, each with its reason); `package.json` `overrides` patch postcss, brace-expansion, compression, source-map-js and undici (Expo CLI's, to 6.29.1). Remove an exception once a fix can be installed.

### App CMS (remote layout)

The separate **The-Nura-CMS** portal controls parts of the app through `period-buddy-be`'s public `GET /api/app-config`, so none of this needs a release.

**Files:**
- `lib/appConfig.ts`: pure types, parsing, selectors and tests (`lib/__tests__/appConfig.test.ts`).
- `components/app-config.tsx`: `AppConfigProvider`, which sits above `ThemeProvider`.
- `hooks/useViewer.ts`: who is looking, for audience rules.
- `lib/tapAction.ts`: runs tap actions (in-app routes go through the launch route guard).
- `lib/launchGuard.ts`, `components/AppConfigSync.tsx`, `components/LaunchSheet.tsx`, `components/LaunchTileParts.tsx`, `lib/deviceId.ts`: launch states (below).

**What the CMS controls:**
- **Feature tiles:** which of the built-in `FEATURE_REGISTRY` features show, and where. The places are the three hubs plus a **Shortcuts** block on Home (`home` placement, the `shortcuts` home section, last in the default order) and Profile (`profile`, via `components/CmsShortcuts.tsx`, which draws them as rows of four round quick-action icons with labels and no heading, ignoring tile size).
- **Tile look:** order, size (`small` grid tile or `large` row), colour, text, badge and audience (signed-in / premium / free, platform, app-version range).
- **Admin link tiles** (`customTiles`): open a route, a website (`expo-web-browser`), or **another app** via `Linking.openURL(value)`, falling back to `fallbackUrl`. A tile with no action (`type: "none"`, or an unsafe one parsed down to it) is a Coming soon teaser for something not in the app yet: it shows only while locked, and `hubTilesFor` drops it for anyone it would resolve to `open` for.
- **Screen layouts:** order and visibility of the blocks on Home (`homeSections`), Profile and the three hubs (`screenSections`, read with `shownSections(config, screen, viewer)`, which also applies each block's `audience` and `startAt`/`endAt`). `sectionText` gives a block's heading/intro override, and `screenTitles` renames hubs (also on Home's hub cards). The hubs share `components/HubScreen.tsx` (intro as the header subtitle, promo banners, tiles). How the tiles are drawn is the app's call (`lib/hubLayout.ts`, unit-tested): one feature per hub can be a **hero** card while it's open (`HUB_HERO`: Care → consultation with a Book a call button, Wellness → Nura AI with our avatar (`components/NuraAvatar.tsx`, also the tab bar's centre button) and a question box that opens `/(app)/qa?new=1&q=…`, which sends it), and built-in features are grouped into titled sections drawn as a `list` (rows in one card) or `tiles` (two-column tinted cards) (`HUB_SECTIONS`). A section sits where its first tile is in the CMS order. Anything not listed there (link tiles, features moved to another hub) falls back to its CMS size: `large` → list row, `small` → grid tile. A new built-in hub feature should be added to a section there. Blocks in `REQUIRED_SECTIONS` (Profile's identity, account, preferences, privacy & help, log out; a hub's tiles) always show, for everyone, whatever the config says.
- **Personal Home** (`lib/homeLayout.ts`, unit-tested; `components/home-layout.tsx`'s `HomeLayoutProvider` in `app/(app)/_layout.tsx`; screen `app/(app)/customize-home.tsx`, Profile → Preferences → Customize Home): on top of the CMS, each person shapes their own Home. Only what the CMS shows that viewer is offered; promo slots stay put.
  - **Blocks** (`CUSTOMIZABLE_BLOCKS`): hide/show and reorder, or start from a template (`HOME_PRESETS`, one per kind of person: On the go / Health focus / Fun & social / Learning my body, all sharing the default top (stats → this week → cycle card → quick log; `order` lists all seven blocks so promo slots stay put, tested); `applyPreset` sets order, hidden, list-block items, headings and the template's shortcuts with their styles, after a confirm if the person had picked their own; each must show the cycle card + quick log, at least 4 blocks, and only shortcuts a default viewer sees (tested); the standard Home is Reset, not a template). A new Home block people may toggle must be added there.
  - **Block options** (`BLOCK_SETTINGS`, `layout.blocks`): renamed headings (Insights, More for you, and optional headings on Quick log / Shortcuts) and picked items: `statPills` from `STAT_OPTIONS` (values computed in `home.tsx`'s `statValues`), `quickActions` from `lib/logFocus.ts#LOG_FOCUS` (each opens `/(app)/tracker?log=today&focus=<key>`; `DayDetailsModal` scrolls to it via `recordSection`, so a new key needs one there), `moreForYou` hub areas. Back to defaults = the entry is dropped.
  - **Shortcuts**: picked from any hub's tiles (`shortcuts: null` = the CMS's `home` tiles, max 12), each with its own `shortcutStyles` entry: look (`icon` round / `tile` small hub tile / `card` large hub tile), colour (`TILE_COLOR_KEYS`), name (≤ 24) and icon (`ICON_CHOICES`); null = the tile's own. Drawn by `components/HomeShortcuts.tsx` (icons via `CmsShortcuts`, tiles/cards via `HubFeatureTiles`), also the screen's live preview.
  - **Saving**: per account via `authApi.getHomeLayout`/`saveHomeLayout` (`/api/auth/home-layout`, debounced and sent one at a time — a save is marked clean only if it is still the newest edit; text fields save on blur and on unmount), with a per-account AsyncStorage copy (`period-buddy.home-layout.<id>`). Unsent edits (`dirty`, stamped `editedAt`) go out on the next launch only if the server copy's `updatedAt` isn't newer; otherwise the server layout wins. `ready` turns true once that copy is read, and Home shows skeleton blocks until then (no flash of the default layout). Picking a template over a customized layout asks first. The backend only shape-checks keys (`utils/homeLayout.js`); the app owns their meaning.
- **Feature usage** (`lib/usage.ts`): `AppConfigSync` counts an `open` when a feature's screen is entered (`featureForRoute`), `useTilePress` a `tap` on an open tile; batched to `POST /api/app-config/usage` every 15 s, at 20 events or on backgrounding. Fire and forget.
- **Theme:** brand, surface and text colour overrides per mode, merged into `components/theme.tsx`.
- **Promo banners** (`components/PromoBanners.tsx`): Home top/middle slots, hubs and Profile, plus a once-per-device **popup** over Home (`components/PromoPopup.tsx`, its own `Modal` because `AppModalHost` only renders alerts). Clicks and impressions are beaconed, impressions once per session.
- **Launch states** (spec: The-Nura-CMS `docs/launch-states.md` §4 and §7.3): each feature and link tile carries a `launch` the backend has already decided for this user or device. The values are `open`, `soon` (Coming soon: a dimmed tile with a SOON pill replacing any badge, and no chevron on large rows) and `paused` (a pause dot, badge hidden), plus an optional BETA pill. `openFor` + `fallback` narrow `open` to a rollout slice that is matched against the viewer; `fallback: "hidden"` drops the tile (`resolveLaunch` in `lib/appConfig.ts`). A locked tile's tap opens `components/LaunchSheet.tsx`, a bottom sheet rendered by `AppModalHost` as a `kind: "launch"` request (`showLaunchSheet` in `lib/modal-host.ts`), with Notify me (`appConfigApi.notifyLaunch`, optimistic) or the paused alternative action. Soon taps are beaconed (`trackLockedTap`). **Route guard:** `guardRoute()` in `lib/launchGuard.ts` (called by `runTapAction` for routes, and in `AppShell`/`notifications.tsx` before pushing a push-notification or shared-link target) opens the sheet instead of a locked feature's screen. A route belongs to a feature when its path equals the feature route's path or sits under it, ignoring groups and the query (`launchForRoute`). `components/AppConfigSync.tsx` (in `AppShell`) mirrors config + viewer into the guard and refetches the config on sign-in/out. `isFeatureVisible` is true only when the feature is actually usable.
- **App settings** (`components/AppGate.tsx`, mounted in `AppShell`): maintenance mode blocks the app. Below `minVersion` the app is blocked with the store link. Below `latestVersion`, or for everyone when the CMS sets `forceShowAll`, an update bottom sheet (app icon, "What's new" `highlights`, `ctaLabel` button, "Later" unless `dismissible: false` for out-of-date users) shows once per `promptId` (else per `latestVersion`; `gateState`/`updatePromptKey` in `lib/appConfig.ts`). It's a plain overlay, not a `<Modal>`. The store button goes through `openStoreLink` (`market://` first on Android). None of this applies on web.

**How it loads:**
- Built-in defaults (today's layout) render first. Then the AsyncStorage cache (`period-buddy.app-config`), then a fresh fetch.
- The fetch is per viewer. It sends the session token attached by hand under `skipAuth`, so a stale token can never sign the user out from here, along with `X-Device-Id` (`lib/deviceId.ts`, a random id per install) and `X-Nura-Launch: 1`. Without that last header the backend hides every item that isn't plainly open, so older builds never show unfinished features.
- It refetches on foreground (≤ every 3 min), on Home's pull-to-refresh and on sign-in/out. A refresh asked for mid-fetch runs again once the fetch lands.
- Every failure is silent, and anything malformed or unknown falls back to the default.

**Adding a feature:** add it to `FEATURE_REGISTRY` here **and** to `constants/appCatalog.js` in the backend (same key, route, placement). A key only one side knows is ignored by the other.

### Data layer (`lib/api/`)

All backend access goes through one folder, imported as `lib/api` (its `index.ts` re-exports everything, so import paths never name a file inside it): `client.ts` holds the HTTP client and typed request helpers (`apiRequest`, `apiEnvelopeRequest`) and one file per domain (`auth.ts`, `cycle.ts`, `consultation.ts`, `community.ts`, `content.ts`, `partner.ts`, `ai.ts`, `schemes.ts`, `subscription.ts`, `support.ts`, `genz.ts`, `appConfig.ts`, `upload.ts`) holds its types and its `xApi` object (`authApi` (incl. `getHomeLayout`/`saveHomeLayout`), `cycleApi`, `habitsApi`, `forestApi`, `consultationApi`, `subscriptionApi`, `partnerApi`, `buddyApi`, `nominationsApi`, `communityApi`, `blogsApi`, `reelsApi`, `healthIssuesApi`, `wellbeingApi`, `questionAnswerApi`, `voiceAgentApi`, `uploadApi`, `documentApi`, `speechApi`, `reportApi`, `insightsApi`, `screeningApi`, `schemesApi`, `schemeApplicationsApi`, `genzApi`, `circlesApi`, `supportApi`). Every response envelope is `{ data, error, message, ... }`; `apiRequest` unwraps `.data`, `apiEnvelopeRequest` returns the raw envelope (used for auth flows that need `token`/`user`/`isProfileComplete` alongside data). `healthApi` just wraps the `/health` liveness check.

Day keys are always local (`getDateKey`), never `toISOString().slice(0, 10)`, which is the UTC date. Cycle dates from the server (`currentPeriodStartDateISO`, `actualPeriod*ISO`, `lastPeriodStartDate`) are calendar days stored as UTC midnight: read them with `dateFromDayKey` (`lib/format.ts`), never `new Date(iso)`, which lands on the previous day west of UTC. "Today" on long-lived screens comes from `useTodayKey()` (`hooks/useTodayKey.tsx`; `TodayWatcher` in `AppShell` rolls it over at midnight and on foreground and emits `cycle`/`dashboard` so predictions refetch), not a `new Date()` read once. A failed day-log save calls `alertLogNotSaved` (`lib/alert.ts`) instead of being swallowed.
- **Cross-screen refresh (`lib/data-sync.ts`, `hooks/useDataRefresh.ts`)**: dashboard tabs and any screen lower in the stack stay mounted, so a one-time fetch-on-mount goes stale when another screen writes. `apiEnvelopeRequest` calls `emitMutation()` after every successful non-GET, and `topicsForMutation()` maps the endpoint to `DataTopic`s (`cycle`, `dashboard`, `profile`, `subscription`, `notifications`, `qaSessions`, `schemeApplications`, `documents`, `partner`, ...; unit-tested in `lib/__tests__/data-sync.test.ts`) — so writes need no manual wiring, but a **new endpoint that changes data another screen shows must be added to `MUTATION_TOPICS`** (requests that bypass the helper, like `documentApi.upload`, call `emitDataChange` by hand; so does a foreground push, via `app/_layout.tsx`). Screens subscribe with `useDataRefresh(topics, cb)` — `cb` runs (debounced) immediately if the screen is focused, otherwise once on its next focus, with `{ whileFocused }` so a screen can skip refetching over its own writes (profile, partner) or do a lighter refetch (tracker) — or with `useAsyncLoad(fetcher, deps, { refreshOn })`. Callbacks must refetch silently (no loader, keep data on failure). `useUserStats`/`useSubscriptionAccess` also drop their 60s module cache on `dashboard`/`subscription`, which is what makes `FeatureGate` unlock after a purchase.
- **Response cache (`lib/queryCache.ts`, unit-tested; persistence wired in `lib/queryCachePersist.ts`)**: stale-while-revalidate for GET data. `fetchQuery(key, fetcher, { staleMs, topics, persist, force })` serves a fresh entry without a request, shares one in-flight request between callers, and caches the result; a mutation on one of `topics` (the `DataTopic`s above) marks the entry stale (kept, so screens still paint, refetched on the next read). `useAsyncLoad(fetcher, deps, { cacheKey, staleMs, persist, refreshOn })` builds on it: a second visit paints the cached copy with no spinner and revalidates quietly; `reload(true)` (pull-to-refresh) always forces. `persist: true` also keeps the copy in AsyncStorage (≤ 7 days) so a cold start paints before the network answers — **public CMS content only**; health data belongs in `lib/secureStorage.ts`. `clearQueryCache()` runs in AuthProvider's per-account clear (memory and device). The most-shared reads go through it inside `lib/api/` itself: `authApi.getProfile`/`getDashboard` (15 s), `cycleApi.getSettings`/`getPredictions`/`getYearLogs` (30 s), each taking `{ force }`; screens' pull-to-refresh calls `invalidateQueries(key or "prefix:")` first. Keys include every parameter that changes the response (`genz:wrapped:<period>:<value>`, `circles:detail:<id>`). Screens on it: hygiene, sexual-wellbeing and health-issues (`useAsyncLoad` + `persist`, 5 min); consultation's unfiltered doctor list (memory, 2 min); the first page of the unfiltered blogs feed and government-schemes list + categories (direct `fetchQuery`/`hydrateQuery`, persisted, 5 min; schemes' profile-ranked recommended strip memory only) — later pages, searches and filters stay live. `cycleApi.getYearLogs(year)` is one `?year=` request for the tracker and calendar (an older backend ignores `year` and returns everything, so it filters by prefix too).
- `hooks/useUserStats.ts` is the canonical source for streak/wallet numbers (`{ streakCount, walletBalance }`); it fetches the dashboard once and syncs it into auth-context. Screens should consume this hook instead of reading `user.streakCount`/`user.walletBalance`/`user.tokenEarned` directly, so streak/points never drift between screens.
- The auth token (keystore, see `lib/sessionStore.ts` above) is attached as `Authorization: Bearer` automatically; pass `skipAuth: true` for public endpoints. `AuthProvider` hands it to `lib/api/` in memory via `setSessionToken()` on launch and before setting the session on sign-in (`null` on sign-out), so screens that mount on sign-in never race the keystore write; `getToken()` only falls back to reading the keystore (cached 30s, but a missing token is never cached) when no session token was set.
- `AuthUser.partnerRole` is resolved client-side after login (`lib/auth.ts#connectPartnerAndResolveRoute`) and never comes back on server user objects, so `auth-context.tsx#updateUser` keeps the existing role unless the caller passes one explicitly (`null` included, as on partner disconnect) — otherwise passing a fresh `authApi.updateProfile()` result would drop it and the partner-view layout guard would bounce a viewer into the owner dashboard. Because the role otherwise lives only on-device, `AuthProvider` re-syncs it from `partnerApi.getProfile()` (`syncPartnerRole`) on every launch/login and app foreground, and `PartnerViewStateProvider.refreshProfile()` pushes the fresh profile's role in too — so an owner-side disconnect (server sets the viewer's role to `null`) or a failed role lookup at login self-corrects via the layout guards. A sequence counter (`roleWriteSeq`) drops sync results that started before a sign-in/out or explicit role write, so the post-login sync can't race `connectPartner()` and overwrite the fresh `viewer` role. `DELETE /api/partner/disconnect` also emits a `partner_disconnected` WebSocket event to both sides' personal `user_<id>` rooms (plus a push to the other side): the partner view re-fetches on it (→ role sync → guard redirect) and the owner's `(app)/partner.tsx` reloads its profile, so either side ending the connection updates the other immediately.
- A 401 triggers a global `onUnauthorized` handler registered by `AuthProvider`, which clears the local session — don't hand-roll 401 handling per screen. It only fires when the token the request carried is still the session's, so a slow request from before a logout/login can't sign the new account out. When the account changes (`signIn` with a different user id, or `signOut`), `AuthProvider` clears per-account data held outside React state: it emits the `dashboard`/`subscription` topics (dropping `useUserStats`/`useSubscriptionAccess`'s 60s caches) `clearStoredAppState()` (saved/reported posts persisted by `components/AppState.tsx`) and `clearForestCache()` (the Forest's offline copy and queued waterings). Day logs/notes in `AppState` are an in-session overlay only and are never persisted on any platform: every save also goes to the server, which is the source of truth. Add any new module-level per-user cache to that list. A response with `code: "ACCOUNT_SUSPENDED"` (403 from login/Google sign-in, 401 mid-session — see `period-buddy-be`'s `utils/accountStatus.js`) becomes `ApiError.kind === "accountSuspended"` (`isAccountSuspendedError()`); on an authenticated request it calls `onUnauthorized("suspended")`, and `AuthProvider` signs out and shows one "Account suspended" alert. On the login screens the server's message just shows in the existing error banner.
- Every request is aborted after `DEFAULT_TIMEOUT_MS` (20s; override per-call with `timeoutMs`, `0` disables) and every failure throws a typed `ApiError` carrying `kind` (`network`/`timeout`/`server`/`notFound`/`unauthorized`/`unknown`) and `status`, plus the server's `code` and the error body as `details` when it sent them. Use the exported `isNetworkError(err)` and `getFriendlyErrorMessage(err)` helpers to branch on connectivity vs. show copy — don't string-match `.message`. `useAsyncLoad` already exposes an `offline` boolean derived from these; `LoadingErrorState` and `EmptyState` take an `offline`/`wifi-off` variant.
- Several types carry `@deprecated` fields kept for backend backward-compat (e.g. `tokenEarned` → `walletBalance`, `likes` → `likeCount`, `views`/`viewsCount` → `viewCount`) — use the non-deprecated field in new code.
- File uploads (`uploadApi.uploadImage`, `documentApi.upload`, `speechApi.transcribe`) bypass the JSON helpers and build `FormData` directly, with a web-vs-native branch (web needs a real `Blob`, native uses the RN `{uri,name,type}` shape).
- Realtime (buddy chat, video call signaling) goes over a WebSocket at `WS_BASE_URL` — construct the URL via `getWebSocketUrl()` so the auth token query param is attached consistently.

### Sharing & deep links

`lib/share.ts` (`shareWithAppLink`, used via `components/AppState.tsx`'s `sharePost` or directly) is the one way to share anything that should reopen in-app: it wraps an in-app path (e.g. `"community?postId=abc123"`) into `https://thenura.care/app?deeplink=<path>`. Don't call `Share.share` directly for shareable in-app content. Current share points and their deeplinks: blog detail (`blogs?slug=`), reel cards in blogs and the Share button on each reel's action rail (`reels?reelId=`), community posts (`community?postId=`), government scheme detail header (`government-scheme-detail?id=<slug>`), partner invite (`partner-connect?code=`), symptom checker results (`symptom-checker`), Bestie Circle invites (`circles?code=`), and the Gen Z share cards' text fallback (`wrapped`, `era`, `badges`). **Every deeplink route's first path segment must be in `lib/deeplink.ts#SHAREABLE_ROUTES`**, or incoming links to it are ignored (the app just opens). Target screens read their id with `useLocalSearchParams` and open the item themselves after mount (blogs → article modal, community → comments sheet, reels → fetches that reel via `getReelById` and pins it first/playing, scheme detail → loads by `id`, partner-connect → prefilled code).

Incoming links: `app/+native-intent.tsx#redirectSystemPath` (expo-router's pre-routing hook, cold start and warm) runs every URL through `lib/deeplink.ts#resolveDeepLink`, which recognizes both `https://thenura.care/app?deeplink=<path>` (Android App Link) and `thenura://<route>?...` for shareable routes; anything else (OAuth redirects, dev-client URLs) passes through untouched. For ours it *queues* the target in `lib/deeplink.ts` and returns `/` (cold) or `""` (warm, = don't navigate), so expo-router never lands on the unmatched `/app` route. `AppShell` in `app/_layout.tsx` consumes the queue (`useSyncExternalStore`) and `router.push`es it once the navigator is ready, the user is signed in, and the entry screens (`ENTRY_PATHS`) have redirected to the dashboard — so Back returns to the dashboard, and a logged-out user's link stays queued (in memory) until they log in. `PUBLIC_DEEP_LINK_PATHS` (just `/partner-connect`) opens without waiting for login. `/community` is rewritten to `/forum` for partner viewers. Every push adds an `openedAt` timestamp param so an already-mounted screen (the community tab) re-opens the item when the same link is tapped twice. Don't add a separate `Linking` listener for these — that was the old duplicate handling.

Android App Links: `app.json`'s `android.intentFilters` (https, `thenura.care`, `pathPrefix: /app`, `autoVerify: true`) needs `https://thenura.care/.well-known/assetlinks.json` (marketing site repo `The-Nura-Marketing-Website/public/.well-known/`, served as JSON by its `vercel.json`) to list the **Play Console App signing key SHA-256** (it lists three fingerprints and is live; Google's Digital Asset Links API resolves it to `com.uvin124.thenura`). If the signing key ever changes, add the new fingerprint there or Android stops verifying and the https link opens the browser instead. The browser fallback is that repo's `src/pages/AppRedirect.jsx` (`/app` route): on Android it navigates to `intent://<deeplink>#Intent;scheme=thenura;package=com.uvin124.thenura;S.browser_fallback_url=<Play Store with referrer=deeplink=...>;end` (works in Chrome and most in-app browsers; also offered as a button since some webviews need a real tap), iOS/desktop get buttons. The Play Store `referrer` is set but not read by the app yet (no install-referrer library, so no deferred deep link after a fresh install). `ios.associatedDomains` + `apple-app-site-association` (placeholder Team ID) are there for when iOS ships. Intent filter / scheme changes need a new native build; test with `adb shell am start -a android.intent.action.VIEW -d "<url>"`.

### Styling

NativeWind (Tailwind for RN) via `tailwind.config.js` / `global.css`, plus `components/theme.tsx` (light/dark, hydrated before first paint) and `components/ui-tokens.ts` for shared design tokens (including `getSeverityColor` for danger/warning/success by numeric threshold). `ThemeColors` has two extra category accents beyond the rose/lavender/mint trio — `sky` (blue) and `gold` — added for the day-log modal and Graphs & Reports; `getSoftTints`/`getLogCategoryTints` (`ui-tokens.ts`) expose them alongside the rest as pale-bg/solid-fg pairs. **Dark theme ("Plum night"):** not black — layered shades of one deep aubergine: `background` #1B1424 → `surface` #2A2136 → `surfaceSoft` → `surfaceStrong` #3D3149, with `border` #4A3D58 visible against cards, so every surface and edge is easy to see. Bright but not pure-white text (#F5EFF8), helper text #C2B5CC, clear soft accents (pink `primary` with dark `buttonText`); every text token clears ≥5.4:1 on `surfaceStrong`. Keep it glare-free: no coloured glows in dark (`getGlow(color, isDark)` returns a plain soft shadow there); saturated white-text cards use `getHeroGradient`'s jewel tones (berry → plum → indigo), never the accent tokens. Dark cards get a light 1px ring and top inner highlight from `getShadow` (top highlight on Android 10+). Users found pure-black too harsh and a muted version hard to read: keep text bright and surfaces distinct. **Depth:** `getShadow(colors, isDark)` is the one card shadow: a layered `boxShadow` (hairline ring + contact shadow + soft plum-tinted ambient; a faint light edge in dark mode), falling back to the legacy shadow/elevation props on Android below API 28; don't add `shadowOpacity`/`elevation` overrides after spreading it (Android would draw both). `getGlow(color, isDark, "soft" | "strong")` is the coloured glow (light theme only; dark gets a plain shadow) under filled accent elements (Home's hero card, today's day, the primary quick action); `withAlpha(hex, a)` makes rgba from a theme hex. Big numbers use `fontWeight: "800"`, negative `letterSpacing` and `fontVariant: ["tabular-nums"]`; small icon squares and big cards use `borderCurve: "continuous"` (iOS squircle corners).

**Icons:** every icon goes through `components/Icon.tsx` (`<Icon set="ion" | "feather" | "mci" name=… />`), which draws it from **Lucide** (`lucide-react-native`, one consistent outline set over the existing `react-native-svg`) by the old Ionicons/Feather/MaterialCommunityIcons name; a solid Ionicons heart/star/bookmark/water/flame/moon is drawn filled. Names with no Lucide match (brand logos, anything new from the CMS) fall back to the original set, so add a mapping in `LUCIDE` when you use a new name. Don't render `@expo/vector-icons` components directly. Avoid sparkle icons for AI features: Nura's own `NuraAvatar` marks the AI.

**Fonts:** exactly two typefaces app-wide — Manrope (`fonts.heading`/`fonts.body`) for all headings and body copy, IBM Plex Mono (`fonts.mono`/`fonts.monoSemiBold`) for numeric/code-like content (streaks, OTPs, stats). IBM Plex Mono and the icon fonts (`Ionicons`/`Feather`/`MaterialCommunityIcons`, preloaded behind the splash so icons don't pop in late — add any new `@expo/vector-icons` family there too) load in `app/_layout.tsx` via `useFonts`. **Manrope is embedded natively, not loaded at runtime:** the `expo-font` plugin in `app.json` builds one `Manrope` family from the static `assets/fonts/Manrope_<weight>.ttf` files (300–800), so plain `fontWeight` picks the right file. Android can't pick weights from a variable font (it renders the ExtraLight default), and a runtime font with the same name would replace the family, so `Manrope-Variable.ttf` loads at runtime **only on web**. Font changes need a new native build. Don't add other font families without updating `ThemeFonts` there too. Text without an explicit `fontFamily` still gets Manrope from `lib/react-native-shim.tsx`: `metro.config.js` points app code's `react-native` import at it (`node_modules` keeps the real one), and its `Text`/`TextInput` add `fontFamily: "Manrope"` before the caller's style. `Text.defaultProps` can't do this, since React 19 ignores `defaultProps` on function components. The shim also gives `TouchableOpacity` a default `activeOpacity` of 0.7 (React Native's 0.2 is a harsh flash); pass one only to deviate. The shim is written as JSX so NativeWind still handles `className`.

**Motion and feel:** `components/motion.ts` holds the shared timing (`motion.duration.fast/base/slow` = 150/220/320, `motion.easing.enter/exit`, `motion.spring`) plus `listEntering(index)` (fade-up for the first rows of a list on first load; Home sections, notifications, community, articles use it; pass it only for the first screenful) and `fadeIn`. Use these for new animations instead of picking per-screen numbers; Reanimated already skips/shortens them under the system "reduce motion" setting. **Bottom sheets:** every partial-height sheet over a dimmed screen is `components/BottomSheet.tsx` (backdrop fades while the sheet springs up, grab handle swipes it down, backdrop/back button close it with the same slide; app-lock cover included; `overlay` for an inline `AppModalHost`; `animateOutBeforeClose={false}` when `onClose` may ask "discard?" or refuse, e.g. `DayDetailsModal`, `PaymentSheet`; `onDismissed` fires after the slide-out, after the Modal's own dismiss on iOS). Don't hand-roll `<Modal animationType="slide" transparent>` sheets; full-screen `presentationStyle="pageSheet"` modals stay native. **Press feedback:** big cards and tiles use `PressableScale` (Hub tiles, article/video tiles, doctor cards, Home quick actions, CMS shortcuts); rows and small controls keep the default dim. **Haptics:** `lib/haptics.ts` (`tap`/`select`/`success`/`error`, no-op on web): success when a day log, habit, payment or booking goes through, error when a save/payment fails, tap on likes and votes, select on `FilterChips`. **Images:** remote images use `expo-image` (`Image` from "expo-image", `contentFit`, `transition={motion.duration.base}`; registered with `cssInterop` so `className` works), not React Native's `Image`; private ones (document previews, photos picked for upload) pass `cachePolicy="memory"` so health images never hit the disk cache. **Celebrations:** `components/celebrations/Lottie.tsx` (`SuccessCheck`, drawn in every `UndoToast` with the `checkmark-circle` icon; `CelebrationBurst`, behind a habit's check when it's ticked and behind the badges streak flame) plays `assets/animations/*.json`, generated by `scripts/generate-lottie.py` and recoloured from the theme via `colorFilters` (layer names are the keypaths); `.web.tsx` shows a still icon since web would need `@lottiefiles/dotlottie-react`. expo-haptics, expo-image and lottie-react-native are native modules: changes to them need a new native build.

**Controls kit (use these, don't hand-roll):** `components/Button.tsx` is the one button (pill, springy press; `primary` filled with a glow and top sheen, one per view; `secondary` surface + card shadow; `tonal` pale brand tint; `neutral` soft grey for Cancel beside a primary; `ghost` text only; `danger`; sizes `lg` 54 / `md` 46 / `sm` 36 with hitSlop; `loading`, `icon`/`iconRight`, `fullWidth`). The alert dialogs (`AppModalHost`), `EmptyState`, `LoadingErrorState`, `AuthPrimaryButton` and onboarding's `PrimaryButton` all draw it. `components/Chip.tsx` is one selectable pill (unselected on the card shadow, selected filled + glow); `FilterChips` is a scrolling row of them. `components/SegmentedControl.tsx` is for 2–4 views of the same screen (sliding raised thumb on a soft track: consultation New/Past, calendar Month/Year, era categories, check-in schedule). `components/SendButton.tsx` is the round send button at the end of every composer (pale until there's something to send). `components/GradientCard.tsx` is any saturated gradient card carrying white text (sheen, hairline inner edge, glow in its first colour; Home's cycle card, the Book-a-call hero). `components/ActionSheet.tsx` is built on `BottomSheet` and runs the tapped action after the slide-out (`onDismissed`). Stack transitions come from `motion.ts#stackScreenOptions` (iOS-style push on Android, full-screen swipe-back on iOS, theme background behind screens). The shim (`lib/react-native-shim.tsx`) also tightens tracking on Text of 20px and up that sets no `letterSpacing`, and `tailwind.config.js` does the same for `text-xl`/`text-2xl`.

**Errors go in a toast, not under the inputs:** `lib/toast.ts` (`showErrorToast(message, title?)`, `showToast(message, { variant })`) drops a pill in under the status bar (above the keyboard), auto-hides after ~4 s, tap to dismiss, error haptic, announced to screen readers. `components/ToastHost.tsx` is mounted at the root and inside every `BottomSheet`; a plain native `<Modal>` with a form mounts `<ToastHost />` as its last child (see `OtpModal`), since hosts stack and the newest wins. ### Tracker calendar (`app/(app)/(dashboard)/tracker.tsx`)

**One day design everywhere, kept deliberately simple:** every calendar day goes through `components/CycleCalendar.tsx#CalendarDayGrid` (Tracker month pager and week strip, Calendar screen month view). Ordinary days are just their number; a soft circle only where it matters (`dayBand`): logged period → solid rose, predicted period → a dotted rose ring, no fill (`DottedRing`, spins into place when it appears; the year view's tiny `MiniMonth` keeps a soft rose dot), fertile days → soft lavender; today → dark ring. Predicted period days come from the server's cycle, **or** from `lib/cycleCalendar.ts#continuesLoggedPeriod`: today and later days within `periodLength` of the start of a logged run of flow days (stopping at a "not on my period" day, flow `none`) show as predicted the moment one day is logged, without waiting for the server's new cycle start (unit-tested). **Future days are faded (opacity 0.45) and disabled**: they can't be logged and anything on them is a prediction. No joined bands, rings on every day, dots, underlines or icons: each was tried and rejected (people preferred this plain circle version). Motion sits on top of that look without changing it: every day squeezes on press (`PressableScale`-style spring), today has a slow soft ping (`TodayPing`), and a day whose own log changes (logged period or any log added/cleared; not shifting predictions) pops and sends out one ripple (`DayRipple`), in step with the tracker hero. Cells are keyed by date for this. The Tracker's `MonthPager` passes `stagger`, so days arrive in a diagonal wave on first show and on every month change, the month title rolls in from the swipe side, the Today pill zooms in/out, and a month change ticks `haptics.select`. All of it stands still under reduced motion. The year view's `MiniMonth` uses the same meanings as tinted dots, future faded. The key is not printed on the calendar: `CalendarKeyButton` (ⓘ beside the Tracker's month title; a quiet "What the colours mean" link on the Calendar screen) opens a "Reading your calendar" sheet; a day's phase shows when you tap it. **Day log loading:** opening a day calls `ensureDayLoaded` (re-requests its year if it failed), and if it still can't load, `DayDetailsModal`'s Save becomes "Couldn't load · Try again" (`loadFailed`/`onRetryLoad`) instead of spinning forever; save failures show the error toast (`alertLogNotSaved`). Home's week strip is separate (today filled, period/fertile tinted). **Opening position:** the Tracker's `MonthPager` draws **only the selected month** (no horizontal list of months): arrows, Today and a horizontal swipe (`PanResponder`, capture variant so a swipe starting on a date still counts) change `year`/`month` and the new month slides in. A 192-month horizontal `FlatList` used to back it and kept mis-positioning itself on Android (opening on January 2020, drifting years back after Today, sliding left/right on its own); don't bring that back. The Calendar screen's vertical month/year lists open on the right month via a start index fixed per opening (`monthStartIndex`/`yearStartIndex`) plus `contentOffset` and a one-time pin on first `onLayout`. It also ignores month-list viewability reports until one includes the month it opened on. Don't add per-screen day styling. The ring in the tracker's cycle card (`CycleRing`) is read-only: a blush track with the estimated 6-day fertile window as a lavender band, "N days late" as its big value while late, the progress arc in the phase colour, phase label, one big value, "Next period <date>" during a period, and a "High fertility" line only inside the estimated fertile window (never "low fertility": a calendar estimate can't promise a low-risk day; hidden when `predictions.ovulationReliable` is false).

The calendar card still renders all 12 months of the selected year stacked and scrollable (`calendarMonths`), but the initial landing on the current month is instant, not animated: the month list stays hidden (`calendarRevealAnim`, opacity 0), and its container clamped to `CALENDAR_LOADING_HEIGHT` with `overflow: hidden` (a `Loader` sits over that clamped area), until the first `scrollTo({ animated: false })` — driven by `monthLayouts` from each month's `onLayout` — has landed on `selectedMonthIndex` (initialized to today), then fades in already positioned there, so opening the tracker never shows a visible "scrolling to current month" motion. `hasInitialScrolled` (a ref, claimed the instant the jump is scheduled — not after it runs, so a second `onLayout` arriving in between can't schedule a duplicate one) gates that one-time instant jump. Expanding the container to its true height (`setIsCalendarRevealed(true)`) and calling `scrollTo` are deliberately **not** in the same tick: the container's expansion is itself a state update the native/DOM side hasn't re-measured yet, so a same-tick `scrollTo` targets a y position beyond what the still-clamped content currently allows and silently comes up short (reproduces identically on native and web — this bit it before, see git blame if it regresses again). A nested double `requestAnimationFrame` after `setIsCalendarRevealed(true)` waits for that re-layout to actually land (one frame for React's re-render, one for the paint) before scrolling and starting the fade. Every later month change (chevrons, the "Today" pill shown once you've navigated away from the current month) scrolls smoothly instead, since by then the container is already at full height and it's a deliberate, visible action. The 4-phase legend (`phaseLegendRow`) is defined once and rendered twice — inline at the top of the calendar card, and as a floating copy in the fixed header (`showFloatingLegend`, compares live page scroll offset `pageScrollY` against the calendar card's measured top `calendarSectionY`) that takes over once the in-card legend has scrolled out of view, so the phase colors stay reachable without scrolling back to the top.

- **`groundShadow={false}`** when the scene casts its own shadow.

`forest.tsx` shows `ForestSkeleton` (sky-and-meadow scene with the `Loader`, then placeholders; never fake "Seed"/"0 of 3" values) until the status has loaded *and* the opening animation is over (`InteractionManager`, with a 700 ms timer fallback because `runAfterInteractions` can wait forever), an error card with Try again if the first load fails (the request aborts at 12 s and a screen watchdog at 15 s, so the skeleton can't hang), then fades the page in. It renders the habitat with the live tree, shows a one-time "Drag to look around · tap your tree" hint, and reuses `LivingTree` (`growth={1}`, `lowDetail`) for each past cycle in the history list, drawing the newest `GROWN_PREVIEW` (9) until "Show all N trees".
- **Offline copy (stale-while-revalidate, `lib/forestCache.ts`):** the last status per account is kept in the keystore via `lib/secureStorage.ts` (it's derived from health logs), packed under 2 KB by `lib/forestView.ts#packForestStatus` (unit-tested). It draws at once, the server's answer replaces it, and a small line above the scene says "Syncing… / Offline · Last synced …". A watering made offline is queued (`queueWatering`, shown done at once via `withOfflineWater`) and sent by `flushWaterings` before the next status fetch: on open, on foreground, on pull-to-refresh and every 30 s while offline on the screen. `clearForestCache()` is in AuthProvider's per-account clear.
- **Cost:** the growth tween lives in `TweenedHabitat`, so only the scene redraws per frame; every scene part is memoized; `active={focused}` stops all loops while another screen is on top; `lowDetail` (low-memory/old phones, `expo-device`, `shouldUseLowDetail`) thins particles, hill trees and the main tree's detail.

### Video calls: Jitsi only (`components/JitsiCall.tsx` / `.web.tsx`, `lib/jitsiCall.ts`)

Every video call runs on the self-hosted Jitsi server `meet.thenura.care`: doctor consultations and Period Buddy calls. There is no other video path. The old WebRTC calls (`ConsultationVideoCall`, `BuddyVideoCall`, `lib/callMedia.ts`, `react-native-webrtc`) were removed, and the backend no longer relays call signaling. `JitsiCall` is one full-screen call for both. Its caller passes `fetchJoin` (`consultationApi.joinVideo(id)` / `buddyApi.joinVideo()`, a fresh short-lived token on every (re)join, so never cache it), optional `onAttendance` (consultations only, informational), and `endedMessage`. Set `endedMessage` when the session ends elsewhere: `consultation_cancelled`/`consultation_completed` on the personal socket, or `buddy_ended`. The call then hangs up with no Rejoin, and a join still in flight is dropped.
- **Consultations** (`consultation.tsx`): the screen has two tabs, **New** (search, live bookings, the doctor list and time picker) and **Past** (finished/refunded sessions; their Book again switches back to New). It opens on New, a list of doctors; **Available slots** / Book again / the profile's **Book slot** (`slotsOpen`) opens `SlotPicker`, a bottom sheet with the doctor's open days and times (grouped Morning/Afternoon/Evening) and a footer with the picked time, fee and Continue; nothing is preselected. Continue closes the sheet and starts payment after `SHEET_DISMISS_MS` (two native Modals can't present at once); `BookingBar` then only shows the payment status while `booking`. Each live booking is a plain card with a status pill, the time, **Join video call** (when it has `videoCall`; enabled inside `joinOpensAt`–`joinClosesAt`, re-checked every 30 s, `isJoinWindowOpen`) and **Chat**. It's disabled with "Video calls aren't available right now" when `videoCall.available` is false. The chat header's video button and the ringer's Accept (`?id=&call=1`) open the same call.
- **Buddies** (`buddy-nomination.tsx`): a call needs **both** buddies online in the chat. The video button only works while the buddy's presence shows online; offline shows the "is offline" alert. The API checks the same thing (409 `BUDDY_OFFLINE`/`BUDDY_CHAT_NOT_OPEN`, shown with Try again). The other buddy gets a "started a video call · Join" prompt in their chat, which is cleared when the caller goes offline. Buddy calls never use the app-wide ringer or a push.
- **In-call chat:** `JitsiCall`'s optional `chat` prop (`CallChat`) shows the **existing** chat in `components/CallChatPanel.tsx`, a sheet over the video with an unread badge on its button. Android back closes it before leaving the call. It holds the same messages and uses the same send function as the chat screen, so everything is saved and encrypted. There is no separate Jitsi chat. The consultation screen loads the call's consultation chat without opening the chat sheet (`openChat(c, { show: false })`) and keeps its room socket open while the call is (`chatInCall`). The buddy screen passes its `chatLog`.
- **Ringing:** `IncomingCallOverlay` is for consultations only ("your doctor is waiting"). It stays quiet for the call you're in (`setOpenVideoCall` in `lib/consultationPresence.ts`). Decline tells the doctor. List rows for old call pushes open the screen without `call=1` (`resolveNotificationTarget` with `joinCall: false`).
- **Errors:** refusals come back as `ApiError.code` (`JOIN_WINDOW_NOT_OPEN` with `details.opensAt`, `JOIN_WINDOW_CLOSED`, `CONSULTATION_NOT_LIVE`, `PAYMENT_REQUIRED`); `describeJoinError` turns them into copy.
- **Why not the native SDK:** no `@jitsi/react-native-sdk` release supports RN 0.81 (12.x needs 0.79, 13.x needs 0.85). So it's Jitsi's web client in `react-native-webview`, through the IFrame API (`buildJitsiHtml`). Jitsi's toolbar is hidden, and the screen's buttons (mic, camera, audio only = low-bandwidth mode + camera off, leave) are the only controls, so there's no invite. The WebView loads only `https://<domain>/…` (`onShouldStartLoadWithRequest`).
- **Permissions:** Android camera/mic go through `PermissionsAndroid` first. No mic shows Open Settings; no camera joins with video off.
- **Call states:** waiting-for-the-other-person, offline, expired-token, dropped-call and blocked-device states come from `applyJitsiEvent` (unit-tested), and fatal ones offer Rejoin. `expo-keep-awake` keeps the screen on.
- **Builds:** removing `react-native-webrtc` needs a new native build. Test calls on an Android dev build.

### Voice input

`hooks/useVoiceInput.ts` wraps `expo-audio` recording (with metering enabled) behind `{ handleMicPress, isRecording, isTranscribing, level }`: tap-to-start/tap-to-stop always works, and when `voiceMode` is true it also auto-stops and transcribes after ~3s of on-device silence (via live dB metering), calling `onTranscript`. `components/VoiceOrb.tsx` is the reusable animated mic (Reanimated pulsing rings driven by `level`, themed via `colors.primary`/`colors.accent`/`colors.danger`). `components/VoiceModeOverlay.tsx` is a full-screen `Modal` — centered large `VoiceOrb`, rotating sci-fi sweep rings, and a status line (listening/thinking/speaking) — that `app/(app)/qa.tsx` and `app/(app)/document-chat.tsx` render whenever `voiceMode` is true; both screens share `hooks/useVoiceChat.ts`, which runs the effect that auto re-arms the mic (`handleMicPress`) whenever voice mode is idle (not recording/transcribing/replying/speaking, and not while the reply's audio is still being synthesized, shown as "thinking", or the mic would record the reply and send it back as the user's words), so the mic opens automatically on entering voice mode and after each spoken reply, Assistant-style.

**Voice mode, both ends:** `hooks/useVoiceInput.ts` records speech as mono 16 kHz AAC (small, quick to upload), sends after `SILENCE_TIMEOUT_MS` (1.5 s) of quiet, never uploads a recording with no speech in it, and after two silent rounds in a row sets `listeningPaused` (the screens' re-arm effects check it, so the mic waits for a tap). Replies are spoken by `hooks/useSpokenReply.ts` (`speak(id, text)` / `stop()`, `playingId` / `preparingId`): `lib/voiceSpeech.ts` (unit-tested) strips markdown/links/emoji, chart blocks, images and HTML tags and splits the reply into sentence chunks; chunk 1 is synthesized and plays while the next is synthesized and loaded, so speech starts after one short TTS call. Audio session: recording sets `allowsRecording: true`, playback sets it back to `false` (otherwise iOS plays through the earpiece), both with `playsInSilentMode`. TTS cache files are deleted after playing (`releaseAudioUri`). Tapping the orb while a reply is playing interrupts it and starts listening (barge-in); leaving voice mode stops playback; filler transcripts ("hmm", ".") are ignored (`isMeaningfulTranscript`). The overlay has one End button (no cancel/share) and live captions (`transcriptPreview` = what was heard, `replyPreview` = the answer); in voice mode errors show there, never as an alert behind the Modal. A spoken yes (English or Hindi: haan, theek hai, हाँ) confirms a pending log unless the sentence also has a no (nahi, मत, don't). `qa.tsx` sends the last 8 turns as `history` to `voiceAgentApi.converse`, and the backend adds the user's cycle context and the phone's local date (`clientTodayKey`).

### Platform-specific files

Some components have a `.web.tsx` variant for APIs that differ between native and web, e.g. `components/JitsiCall.tsx` / `.web.tsx` (WebView vs. the IFrame API straight in the page), and `components/CashfreeCheckoutModal.tsx` / `.web.tsx` (`react-native-webview` ships no web implementation at all — its fallback just renders "React Native WebView does not support this platform" — so the web variant loads Cashfree's JS SDK directly via a `<script>` tag and opens its real browser checkout instead of a WebView; same `onResult` shape either way, so callers never branch on platform). **How people pay:** `components/PaymentSheet.tsx` (Nura's own sheet, no WebView) is what opens first for consultations, subscriptions and the paywall: "Pay with a UPI app" lists the UPI apps installed on the phone (`Linking.canOpenURL` on each `lib/upiIntent.ts#UPI_APPS` probe; Android also gets "Other app" = plain `upi://`, the system chooser; none on web), "Pay with UPI ID" (collect), and "Card, netbanking or wallet", which switches to the hosted `CashfreeCheckoutModal`. Tapping an app calls Cashfree's Order Pay API with `channel: "link"` (`lib/cashfreeUpi.ts#startUpiIntent`, a fresh attempt per tap, native only because its client headers fail CORS on web) and opens that app's own link (`upiAppLaunchUrls`: Cashfree's per-app link, else `upi://` rewritten to the app's scheme, then plain `upi://`; parsing in `parseUpiIntentLinks`, unit-tested). Then it waits: polls `onVerify` every 3 s for up to 3 min, checks at once when the app comes back to the foreground, offers "I've paid · check status" and "Try another way to pay", and does one last check when closed so a payment made just then still counts. Callers' verify treats network errors as pending, not failed. This replaced relying on Cashfree's hosted page for UPI apps, whose app list inside a WebView often did nothing when tapped. The hosted checkout still hands any UPI links it opens to the OS (`handleShouldStartLoad`, `intent://` via `upiLaunchUrls`). `plugins/withUpiAppQueries.js` (Android `<queries>`) and `app.json`'s `LSApplicationQueriesSchemes` must list every scheme in `UPI_APPS`. Changes here need a new native build; see the "Subscriptions / paywall" bullet above and `consultationApi` below for how the two combine. `components/reels/YouTubeReel.tsx` uses `react-native-webview` on native and attaches YouTube's `YT.Player` straight to a DOM node on web; `documents.tsx`'s in-app document/PDF viewer uses `react-native-webview` directly and still hits the "not supported" fallback on web (no `.web.tsx` fix yet). `components/celebrations/Lottie.tsx` / `.web.tsx` (Lottie on native, a still check on web). `lib/ringTone.ts` / `.web.ts` (`startRingTone()`, returns a stop function) is the one incoming-call ring: vibration on phones, a Web Audio tone (plus `navigator.vibrate`) on web; used by `IncomingCallOverlay`.
